## État de réalisation (26 octobre 2026)

Le vertical initial est commencé : workspace Cargo à la racine, avec les crates regroupées sous `crates/` (MSRV déclaré à 1.85), façade publique `feluqa::view` et `feluqa::console`, moteur de substitution échappée, application web de référence sous `products/`, serveur Axum/Tokio et config Serde/TOML. Les routes appartiennent au produit; le build génère du Rust depuis les fichiers `.view.rs`.

La page affiche le temps handler « Request … ms ». Le middleware mesure à part le temps complet de traitement côté binaire, l’écrit dans `Server-Timing: feluqa_binary;dur=…` et le journal du serveur. Compilation validée le 26 octobre 2026; parité visuelle et déploiement restent à valider.

État historique au 26 octobre 2026 : le prototype initial n'avait que des vues interpolées simples et aucun watcher. Depuis, le compilateur `.view.rs`, le CLI `feluqa new`, et un premier polling watcher `feluqa dev` ont été ajoutés. Le watcher compile puis redémarre le binaire, garde l'ancien serveur si le build échoue, et n'a pas encore un test de processus complet. Sélection multi-applications, stockage opérationnel, isolation multi-sites, publication autonome, déploiement Hestia et contrôles de production restent à faire. La première milestone n’est donc pas considérée terminée.

## Objectif produit

Feluqa doit devenir un framework applicatif souverain, avec une seule identité (`feluqa`), un workspace Rust et des contrats partagés, tout en gardant des runtimes propres à chaque profil : serveur/API, web client/SPA, desktop, mobile, jeu et temps réel/embarqué. « Une plateforme » signifie des schémas, outils, bibliothèques et conventions partagés, pas un processus universel.

La priorité immédiate est de livrer plusieurs sites web en production. Le premier chemin doit donc permettre à une petite équipe de créer une application, écrire des routes et des vues familières, prévisualiser rapidement, compiler un binaire autonome et déployer sous un compte POSIX ordinaire (notamment derrière Hestia). Les profils client, jeu et embarqué gardent leur place dans l’architecture mais ne bloquent pas cette première livraison.

Le positionnement de l'entreprise propriétaire (contrôle des outils et des données, environnements critiques et haute disponibilité) guide les décisions de propriété des données, de déploiement, de dépendances et d’évolution. C’est un positionnement produit, pas une certification de sûreté ou une promesse de logiciel certifié.

## Principes non négociables

1. Un workspace Cargo et un espace de noms publics `feluqa::`; les applications importent les façades Feluqa, les crates internes peuvent utiliser leurs dépendances directes.
2. Des profils avec des binaires et runtimes différents. Les crates kernel (types, schémas, validation, protocoles) restent aussi indépendantes du serveur que possible et pourront être `no_std` lorsque leurs besoins le permettent.
3. Utiliser des composants éprouvés avant d’en écrire : Tokio (async runtime), Axum (HTTP), Tower (middleware), Serde (sérialisation), tracing (diagnostics), puis un pilote SQLite adapté au besoin. Évaluer Loco comme référence/intégration possible, sans lui déléguer les contrats Feluqa ni confondre sa structure avec notre architecture multi-profils.
4. Configurations et déclarations explicites; aucun balayage de modules ou de répertoires à chaque requête. La compilation de production doit être reproductible et signaler les erreurs de vue à la construction.
5. Les données et fichiers d’application restent sous le contrôle du compte système qui exécute le site. Pas de root requis pour le mode utilisateur.
6. Mesurer avant d’annoncer les budgets de latence, de mémoire ou de taille. Le seuil inférieur à 1 ms reste un objectif du profil serveur et se vérifie sur scénario réel.

```text
│   └── assets/

│   ├── logs/
│   └── sessions/

```

`public/` est l’unique racine de fichiers exposée. `storage/` contient les données mutables; binaires, secrets, SQLite, cache et journaux ne sont jamais servis publiquement. Les chemins par défaut sont relatifs au projet/configurables, avec respect des permissions POSIX et sans écriture dans `/usr`, `/var` ou le home d’un autre utilisateur. Prévoir un mode explicite XDG pour les outils globaux, distinct du stockage d’un site.

Routes déclarées dans des fichiers Rust ordinaires, dans l’esprit de `routes/web.php` et `routes/console.php` Webkernel :

```rust
use feluqa::prelude::*;

pub fn routes(router: Router) -> Router {
    router
        .get("/", handlers::home)
        .get("/about", handlers::about)
        .post("/contact", handlers::contact)
}
```

La syntaxe ci-dessus est indicative; l’API sera arrêtée par un exemple exécuté. Les routes web servent HTTP, les routes console déclarent les commandes CLI. Garder les handlers typés et explicites, et les groupes de routes nommés, préfixes et middleware lisibles.

### Vues Webkernel

Le format cible est désormais `.view.rs` avec notamment `@rs/@endrs`; voir le [contrat v1](../05.reference/05.view-language.en.md). Les `.view` du prototype restent à migrer avec le build.

Inspecter et porter le contrat utile de `webkernel-src/y-dev-platform/...` dans `/home/yassine/Projects/Php/framework/__work/`, en conservant une syntaxe de template familière : `{{ value }}` échappé, `{!! trusted_html !!}` explicite, `@if/@else/@endif`, `@foreach/@endforeach`, layouts/sections et composants `<x-...>`. Adapter les directives qui exécutent du PHP en API de vue déclarative et fonctions Rust typées : aucune exécution PHP ni `eval` dans Feluqa.

La compilation de vues doit être obligatoire pour produire un binaire release : les vues déclarées deviennent des artefacts contrôlés et une vue inconnue/malformée fait échouer le build. En développement, le serveur peut recharger et compiler les vues à la volée pour accélérer le cycle edit-refresh; les erreurs incluent fichier, ligne et colonne. Ne jamais interpréter du code de template fourni par une requête. Les deux moteurs partagent parseur, échappement et règles de rendu pour éviter les écarts dev/prod. Un cache de templates compilés est versionné par empreinte et invalidé proprement.

Livrer d’abord layouts, échappement HTML, variables typées, conditions, boucles, composants/slots, partials et erreurs utiles. Reporters, hooks arbitraires, compilation incrémentale complexe et compatibilité complète Blade attendent un besoin observé. Voir les conventions détaillées dans `AGENTS_VIEWS.md` de Webkernel.

## Architecture du workspace

Structure cible progressive (ne pas créer tous les crates vides à M1) :

```text
feluqa/
├── Cargo.toml                  # workspace Cargo à la racine
├── crates/                     # crates regroupées par domaine
│   ├── Cargo.toml
│   ├── Cargo.lock
│   ├── feluqa/                 # façade publique feluqa::
│   ├── feluqa-kernel/          # types, config commune, validation, no_std possible
│   ├── feluqa-config/          # Serde, chargement et validation de configuration
│   ├── feluqa-view/            # parseur, compilateur, moteur dev/prod
│   ├── feluqa-console/         # API des commandes console déclarées par l'app
│   ├── feluqa-router/          # contrats de routes
│   ├── feluqa-server/          # runtime Tokio/Axum; profil serveur
│   └── feluqa-storage/         # chemins et stockage utilisateur POSIX
├── products/
│   ├── feluqa-cli/             # produit CLI, binaire `feluqa`
│   └── sample-module/          # application consommatrice, profil web
├── target/                    # artefacts de build générés
└── docs-new/
```

Le monorepo est la source de référence. `Cargo.toml` et `Cargo.lock` sont à la racine; `crates/` contient les bibliothèques du framework; `products/` contient les produits exécutables et les applications. Chaque produit garde son manifeste Cargo. La racine du dépôt porte le manifeste Cargo; les builds sont écrits dans `target/`. Les composants Feluqa sont propriétaires et leurs manifests limitent la publication au registre privé.

Chaque crate porte son propre `#![no_implicit_prelude]` à sa racine et importe explicitement les éléments utilisés. Le `main.rs` d’une app générée le porte aussi. Cela ne dispense pas des lints/contrôles par crate : l’attribut ne remplace ni `#![deny(...)]`, ni les règles d’unsafe, ni le formatage. Vérifier tôt l’interaction avec les macros dérivées/proc-macros et les macros d’assertion. Ne pas promettre `no_std` au framework complet : seuls les crates kernel sans dépendance OS peuvent le garantir.

SerDe constitue la frontière de configuration et de sérialisation : définir des structs versionnées, `deny_unknown_fields` sur les configs où une faute de frappe doit échouer, valeurs par défaut explicites, validation sémantique après parse et erreurs contextualisées. Choisir TOML pour configuration lisible, JSON pour interfaces/outils; n’ajouter YAML que si un cas concret le justifie. Les secrets sont référencés depuis l’environnement/fichiers protégés, jamais commités.

## Dépendances candidates

À figer après prototype et contrôle de licence, MSRV, support de cibles, sécurité et maintenance :

| Besoin | Base candidate | Décision de cadrage |
|---|---|---|
| Async I/O | Tokio | runtime du profil serveur; pas du kernel |
| HTTP | Axum + Tower + Hyper via Axum | routeur/middleware du profil serveur |
| Configuration | Serde + `toml` | structs strictes et validation au boot |
| Logs/traces | `tracing`, `tracing-subscriber` | champs structurés, secrets masqués |
| Erreurs | `thiserror` pour erreurs de crate | erreurs d’app explicites, pas de panic sur entrée valide |
| CLI | `clap` | CLI Feluqa; ergonomie compatible commande par commande |
| Stockage SQL | SQLite en premier (pilote à choisir) | benchmark async vs connexion dédiée; migrations versionnées |
| Templates | compilateur Feluqa dédié, Rust natif en sortie | ne pas forcer Askama si la syntaxe Webkernel ne correspond pas |
| Tests HTTP | `tower::ServiceExt` et clients de test | tests de contrat des routes et du rendu |

Éviter les doublons de runtime/framework dans l’application. Une dépendance devient une décision enregistrée avec version/pin, licence, fonction, alternatives et plan d’upgrade. Vendor/mirror selon D-0025 et revalider les licences avant distribution.

## Plan et estimations

Estimations d’effort en **jours-personne (JP)**, pas une date promise. Hypothèse : un ingénieur Rust expérimenté, avec revue produit ponctuelle; le travail dépendant d’un serveur Hestia, DNS/TLS et droits admin peut rallonger le calendrier sans augmenter l’effort logiciel. Les lots se chevauchent peu; recalibrer après chaque gate. Les fourchettes incluent intégration et documentation de base.

| Phase | Effort | Livrable vérifiable | Critère de sortie |
|---|---:|---|---|
| 0. Cadrage et spike Loco/Axum | 3–5 JP | app minimale; versions, MSRV et dépendances décidées; test `no_implicit_prelude` avec macros | une route + une vue rendue, build propre, choix architecture noté |
| 1. Workspace et strictness | 5–8 JP | workspace, `feluqa::` façade, kernel, lint CI, config Serde, logger d’erreurs | exemple compilable; erreurs de config indiquent clé/fichier; aucun `unsafe` non justifié |
| 2. Routes/serveur et CLI dev | 8–12 JP | `routes/web.rs`, `routes/console.rs`, Axum/Tokio, `feluqa dev`, graceful shutdown | nouvel exemple démarre et sert route statique/dynamique; rechargement dev documenté |
| 3. Vues Webkernel v1 | 12–20 JP | syntaxe échappée, layouts, if/loop, composants, slots, erreurs de source, build release | tests de parité dev/build; XSS tests; templates compilés dans l’artefact |
| 4. Fondation sites | 10–16 JP | config, assets/public, formulaires sécurisés, sessions/CSRF, pages d’erreur, stockage POSIX | un site de référence avec pages et formulaire, sans dépendance externe obligatoire |

L’ambition complète (auth, ACL granulaire, cache, jobs, mail, admin/Core, module lifecycle, SDUI/liveview, tous les profils) dépasse volontairement le périmètre de la première plateforme multi-sites; ses phases restent celles de `DECISIONS.md` M1–M8.

## Ordre de livraison conseillé

1. Faire un prototype vertical de site : accueil, page service, page contact/formulaire, layout partagé, assets, 404, routes et déploiement Hestia.
2. Mettre le second site sur la même version du framework pour révéler ce qui est réellement réutilisable (config par site, layouts, contenu, assets, secrets et isolation du stockage).
3. Consolider API de vue et CLI seulement à partir de cette friction observée; garder une checklist de migration des vues Webkernel si des vues existantes doivent être reprises.
4. Ajouter DB/auth/jobs/mail/Core/SDUI par besoins des sites et gates de sécurité, sans retarder le chemin statique et contenu.
5. Geler les contrats partagés et ouvrir chaque profil après son propre smoke test ciblé.

## Risques à suivre

- `no_implicit_prelude` augmente fortement les imports explicites et peut compliquer l’usage de macros générées. Valider un exemple représentatif avant d’en faire une règle de CI universelle.
- Porter toute la grammaire PHP des vues serait un sous-projet de compilateur. Garder la syntaxe familière mais définir une sous-grammaire Rust sûre et des erreurs compile-time nettes.
- Tokio/Axum ne répondent qu’au profil serveur. Ne pas les faire dépendre des crates kernel ou temps réel.
- Plusieurs sites en production nécessitent config/secrets/backup/isolation et rollback, pas uniquement un `cargo run`.
- Les affirmations « souverain », « critique » et « haute disponibilité » doivent correspondre au modèle réel de stockage, aux procédures opérationnelles et au niveau d’assurance atteint.
