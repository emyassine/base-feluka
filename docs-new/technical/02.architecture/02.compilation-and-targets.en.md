This document does not claim a measured speedup or an implemented generated-crate

## What the Feldera experiment teaches us

Gerd Zellweger's [Feldera article, April 15, 2025](https://www.feldera.com/blog/cutting-down-rust-compile-times-from-30-to-2-minutes-with-one-thousand-crates)
describes a large generated Rust program whose compilation was dominated by
LLVM work. Feldera partitioned its operator graph into 1,106 crates, enabling
parallel compilation and reuse of unchanged operators. It reports roughly
30–45 minutes falling to under three minutes in its workload. Content-derived
crate names helped reuse unchanged generated code. Increasing codegen units
alone had not solved that workload's bottleneck.

That result is evidence for measuring and partitioning a dependency graph. It
is not a two-minute guarantee for Feluqa, nor a reason to create a thousand
crates by default. CPU count, memory, graph shape, compiler, optimization and
cache state all affect the result. The article's observations about compiler
parallelism concern its measured toolchain and workload.

## Apply the principle to Feluqa

Feluqa will generate routes, permissions, views, resource schemas and other
metadata. Generation must avoid putting all implementation code into one giant
application compilation unit.

- Keep shared runtime behavior in reusable framework crates. Generate compact
  declarations and calls into that runtime instead of duplicating implementations.
- Separate independent generated domains when measurements identify a costly
  compilation unit. Candidate boundaries include module schemas, view groups and
  resource groups; choose boundaries by dependency and change frequency.
- Keep dependency direction acyclic. Shared contracts sit below implementations;
  the application composition root joins them without introducing a dependency
  from every generated unit back to the application binary.
- Keep small units together when process, metadata and linking overhead outweigh
  parallelism. A Rust file or module is not automatically a separate Cargo crate.
- Review generic expansion at boundaries. Type erasure may reduce repeated
  instantiation where runtime costs are acceptable; benchmark both sides.
- Keep optional BI, UI and web implementations out of unrelated CLI, kernel and
  real-time builds. Preserve the public `feluqa::...` namespace regardless of
  internal compilation boundaries.

Developers should continue writing business code and attributes. Partitioning
must be tooling behavior, not manual per-resource manifests or registrations.

## Deterministic generation and correct reuse

The proposed generator must produce a stable, sorted dependency graph. Generated
source and manifests belong under `target/feluqa/`; ordinary build-script output
continues to use Cargo's `OUT_DIR`. Generated files are never edited or committed.

Write files only when their bytes change. Do not embed timestamps, random IDs or
machine-specific absolute paths into generated identities. Declare the files
and environment inputs that actually affect generation so a no-op build stays
a no-op and a relevant change cannot silently reuse stale output.

A proposed content-derived identity must cover source, generator/schema version,
direct dependency identities and relevant configuration. Compiled-artifact reuse
must also respect compiler/toolchain, target, feature set, profile and flags.
Hashing source alone is insufficient for a custom artifact cache. Let Cargo own
its compilation fingerprints; do not substitute an incomplete homegrown cache.

Generating extra Cargo crates requires a **pre-build orchestration stage** that
materializes manifests and dependencies before invoking Cargo. A proc macro or a
build script cannot be treated as a way to add dependencies to Cargo's already
resolved graph. The CLI must validate the generated graph and invoke Cargo only
after generation succeeds. This stage is planned, not implemented here.

Cache writes must be atomic and protected against concurrent writers. Corrupt or
incompatible entries must cause a diagnostic and rebuild. Bound cache growth and
provide explicit cleanup without routinely deleting the shared `target/` cache.
A cache hit must never bypass validation or authorization of build inputs.

## Keep the workstation usable

The build controller should have a configurable CPU/job budget and a memory
budget, with conservative defaults that reserve capacity for the editor,
browser and running server. Determine those defaults from measurements on a
modest development machine, not a many-core build server.

Cargo job limits alone are not a complete resource limit: individual compiler,
linker and generator processes may use multiple threads and substantial RAM.
Coordinate child processes, respect Cargo's jobserver where applicable, and
measure peak memory and swap pressure. Platform-specific scheduling controls
must have documented fallbacks. Do not hardcode the author's machine limits.

Show generation, dependency resolution, cache/lock waits, compilation and linking
as distinct progress states with elapsed time. Coalesce rapid file changes and
avoid starting competing rebuilds of the same product. Keep diagnostics visible.

During a rebuild, keep the previous HTTP process serving. A compilation failure
must leave that process alive. A future readiness-checked handover must verify
that the candidate starts successfully before retiring the old instance; a
successful compile alone does not establish zero-downtime replacement. Migration
compatibility, port ownership and recovery require their own protocol.

## Measure before choosing optimizations

Record the revision, toolchain, OS, CPU, available RAM, target, profile, features,
job limit, flags, cache state and background workload for every comparison.
Separate dependency download/resolution, generation, Rust compilation, linking
and startup. Use Cargo timing reports to identify expensive crates; use deeper
compiler profiling only when necessary, in a separate target directory so it
does not invalidate the normal development cache.

Compare these scenarios against the same baseline:

| Scenario | Required observation |
|---|---|
| Cold build with dependencies already available | Total work, critical path, peak memory |
| Warm no-op build | No unnecessary generation or compilation |
| One page/resource implementation edit | Actual affected units and rebuild duration |
| Shared contract edit | Correct transitive invalidation |
| Feature, compiler or target change | Correct cache separation |
| Large generated product | Scaling of generation, graph resolution and linking |
| Failed build while HTTP is running | Previous instance remains available |
| Concurrent build or interrupted generator | No partial output or corrupt cache |

Compare representative small and large products, including a projected 100×
source/schema fixture. Record medians and variation across repeated runs and
report warm and cold results separately. Establish numerical regression budgets
from that baseline; do not invent a universal latency target before measuring.

Evaluate crate partitioning, incremental settings, debug information, linker,
LTO and codegen units independently. A faster build must still pass correctness
checks and meet runtime performance requirements. Avoid changing flags on every
invocation, which would undermine cache reuse.

## Business intelligence charts and dashboards

BI visualization is a platform requirement, exposed through the shared
`feluqa::ui` and panel/resource contracts. Products should compose reusable
components instead of implementing their own chart stack. This is a target
capability; this document does not claim that an integrated BI system exists.

The intended catalogue includes KPI/stat cards, line and area charts, bar charts,
scatter plots, distributions, accessible data tables and dashboards. It needs
consistent themes, legends, tooltips, filters, drill-down, date/time formatting,
empty/loading/error states and keyboard-accessible alternatives to graphics.
Exports and live updates must use the same access rules as on-screen data.

Keep visualization schemas separate from query execution and rendering.
Services own tenant-aware, authorized, bounded aggregation; charts receive typed
series and metadata, never credentials or unrestricted database access. Apply
limits, cancellation and timeouts; use aggregation/downsampling for large data
sets. Cache results with tenant, permission scope, query parameters and freshness
in the key, and define invalidation when grants change. A hidden chart is not
an authorization control.

Dashboard filters and refreshed measurements are runtime data. They must not
trigger Rust compilation. Compile reusable renderers once and pass bounded
schemas/data into them. Only trusted developer source changes enter compilation;
do not compile dashboard users' expressions as arbitrary Rust.

Web delivery comes first. Keep schemas reusable for future desktop/mobile
renderers without claiming those runtimes exist. Rendering backend selection,
large-data performance, accessible export and live refresh policies need explicit
implementation and acceptance evidence.

## Delivery and acceptance

1. Capture build timings and workstation responsiveness on representative products.
2. Remove unnecessary generation/invalidation and duplicate runtime code.
3. Prototype partitioning on one measured expensive generated workload; compare
   compilation, memory, binary size and runtime behavior before adopting it.
4. Implement deterministic orchestration and cache failure/concurrency checks.
5. Add the resource-budgeted development build controller and verify HTTP continuity.
6. Deliver a BI dashboard through shared UI components, including tenant-denial,
   large-data, light/dark, accessibility and refresh behavior checks.

Accept changes only with recorded before/after evidence and correctness checks.
Keep planned capabilities marked as planned. Existing deliberate application
breakage after legacy panel removal is a separate issue; documentation does not
repair it or provide a valid application performance baseline.
