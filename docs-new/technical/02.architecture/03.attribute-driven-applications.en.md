## Contract

Application code declares business behavior. Feluqa's compile-time scanner
discovers panels, resources, pages, permissions, gates, modules and typed
configuration, then generates the runtime tables and reference artifacts. App
code does not maintain a second route list, permission registry, navigation
registry or resource registry.

The target entry point is intentionally small:

```rust
#![no_implicit_prelude]
#![deny(unsafe_code, missing_docs)]

extern crate feluqa;

#[feluqa::main]
fn main() {}
```

The scanner discovers `src/panels` and `src/modules` by convention. A path
override is used only when a product deliberately departs from that layout.
Generated module manifests, route/permission tables, config schemas,
`.env.example` and reference docs live below `target/feluqa/`; they are build
outputs and are never hand-edited or committed.

## Source layout

```text
src/
├── main.rs
├── panels/
│   ├── back_office.rs
│   └── customer_portal.rs
└── modules/
    └── sales/
        ├── permissions.rs
        ├── models/customer.rs
        ├── services/refunds.rs
        └── resources/
            ├── customer.rs
            └── customer/edit.rs
```

The module ID comes from its directory. The current `feluqa.toml` and
`module.toml` contracts remain as one-time markers created by Feluqa tooling;
their values are derived from source attributes and `Cargo.toml`.

## Attribute behavior

- `#[feluqa::panel(id = "admin", path = "/admin")]` declares one panel.
  Panel-level `path` is relative to the domain root.
- `#[feluqa::resource(panel = "admin", group = "Shop")]` attaches a resource
  to a panel. The resource's `slug` is relative to its panel. Standard list,
  create, view, edit and delete routes, pages, navigation, forms, tables and
  CRUD permissions are generated from the resource declaration.
- `#[feluqa::permissions]` declares only additional domain permissions. Their
  full names are derived from the containing module. Public variants require
  documentation comments; the comments supply labels and descriptions.
- `#[feluqa::gate(...)]` is required on every data-changing service, action,
  hook or endpoint. Missing gates are compile errors. Several gates combine
  with AND semantics. A deliberately public write must say `public`.
- `#[feluqa::config]` supplies the typed config schema, runtime validation and
  generated environment template.

Context is derived from the scanned source location. A permission inside
`modules/sales` is written `Refund`; a cross-module reference is explicit as
`billing::Invoice`. `feluqa::ui`, `feluqa::panel`, `feluqa::auth` and
`feluqa::resource` are the public namespace roots. Internal package names do
not appear in application code.

## Authorization and privilege levels

The generated permission table is the source consumed by the System panel and
role editor. Resource CRUD capabilities are generated; custom permission
enums cover domain actions that do not map to a resource operation. A role is
a named composition of permissions, and panels may include the shared role,
permission and privilege management resources without duplicating their
declarations.

Platform privilege and module authorization are distinct. Platform privilege
levels may express an instance-wide ceiling such as owner, administrator,
operator or external auditor. They do not grant business-module permissions
implicitly. Module users, tenant roles, record policies and field-level grants
remain separate. Rank and internal/external origin are separate properties;
external origin never creates an application-owner equivalent. Higher-assurance
deployments may require two-person approval or explicit elevation for selected
operations. These controls must be modeled as audited policy, not as a UI-only
role label.

## Scanner and generated artifacts

The scanner is build-time tooling and reads Rust syntax without executing app
code. It resolves the enclosing module from the conventional source tree,
validates duplicate slugs/IDs and unknown references, checks docs and required
gates, and emits deterministic tables. Proc macros validate local syntax and
expand typed declarations; the scanner resolves cross-file context and
references. Neither phase evaluates user-supplied runtime data.

`target/feluqa/` contains generated manifests, routes, permissions, config
schemas, environment examples and reference documentation. Cargo's compiled
output remains under its normal target profile directory. Generated files are
not source of truth and are excluded from version control.

## Current implementation status

This is the target contract, not a claim that all attributes or generated
runtime tables already exist. `feluqa-build` now scans Rust files under the
conventional panel and module roots, skips `.view.rs` templates, derives the
top-level module directory, validates basic duplicate IDs/slugs and panel
references, checks documented permission/role variants and requires a gate on
scanned `post` and `action` functions. Numerimondes invokes it from its build
script and writes a deterministic declaration inventory to
`target/feluqa/numerimondes/declarations.toml`.

That inventory is not yet the generated runtime, route, permission or
configuration system described above. Numerimondes currently has no v2
declarations, so its inventory is empty. It still uses manual panel/resource
registration, explicit route composition and hand-maintained configuration;
`#[feluqa::main]`, panel/resource/page/permission/config attributes, typed gate
expansion, generated permission management and automatic runtime wiring remain
to implement. The scanner is an initial build-tooling foundation. `feluqa/imagery`
remains the shared first-party image and icon capability.
