## How Feluqa is structured

- The workspace groups crates by domain. Native OS shells live outside Cargo.
- Select platform behavior with Rust `cfg` and additive Cargo features, not numbered source folders.
- Rust `mod` organizes source. A crate is the package boundary for dependencies and target support.
- Keep shared core code usable without `std` where the target requires it. Keep server runtimes out of those crates.
- The WebAssembly Component Model is the target default for installable modules. Static linking is the current bootstrap path; arbitrary Rust `cdylib` loading is not a stable module contract.
- Version contracts across crates and module boundaries. A target is supported only after its CI lane and runtime behavior are verified.

## Agent and supply-chain support

Commands should provide structured output. Schemas should define the contract agents use. Modules declare capabilities, and the host denies undeclared access. Keep dependencies pinned, reviewed and vendorable where needed. Use established libraries for cryptography, TLS and protocol parsing.

## Build and reporting

Measure build time and workstation resource use before changing crate boundaries or compiler settings. Generation must be deterministic, and Cargo owns compiled artifact fingerprints. BI dashboards use authorized, bounded data services; changing dashboard data must not trigger Rust compilation.

These are the selected architecture rules. A target in the architecture is available to app developers only after the implementation and acceptance work is complete.
