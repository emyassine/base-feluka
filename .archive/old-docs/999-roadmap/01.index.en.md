# Feluqa roadmap

The roadmap is grouped by concern. Each task file owns one action or major change, its prerequisites and its acceptance evidence. All listed work is incomplete; this documentation reorganization does not establish new runtime verification.

Read a task's prerequisites before starting it. Shared views and components precede System Panel integration. Web delivery comes first. Estimates are planning ranges, not dates; do not add overlapping historical estimates into a release commitment.

## Maintaining the roadmap

Keep each deliverable in one task file under its owning concern. Cross-cutting work has one owner; link to it from dependent tasks instead of duplicating it. Keep the root index limited to concerns and each concern index limited to its tasks. Link to prerequisites and settled guide contracts instead of copying their requirements. Split a task when it acquires an independently deliverable major change. Preserve existing F, CR and AN identifiers when splitting or completing work.

Record verification with the implementation change. Move settled behavior into its guide and remove completed work from the active list. A checked historical item is not evidence that the current checkout passes.

The [earlier planning records](../technical/roadmap/01.index.en.md) retain source provenance and historical estimates. This index and its task files own active sequencing and acceptance.
