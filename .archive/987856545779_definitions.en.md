## Les trois niveaux

1. **Workspace source de Feluqa** : le dépôt qui développe le framework.
2. **Workspace développeur** : un dépôt qui utilise Feluqa et peut gérer un ou plusieurs modules. Il peut être un monorepo, mais ce n’est pas le monorepo du framework.
3. **Package Feluqa** : une crate du framework ou un module développé avec lui.

Le `.feluqa/workspace.toml` identifie le rôle du workspace.
L’attribut identifie les packages qui doivent avoir un `feluqa.toml`.

### Workspace du framework Feluqa

À la racine du dépôt, dans `.feluqa/workspace.toml` :

```toml
[workspace]
kind = "framework"
name = "feluqa"
crates = "crates"
products = "products"
tools = "tools"
git = "https://github.com/emyassine/base-feluka.git"
```

### Workspace d’un développeur

À la racine de son dépôt, même s’il gère plusieurs modules :

```toml
[workspace]
kind = "developer"
modules = ["modules/*"]
```

Ce dépôt peut aussi contenir d’autres dossiers; il n’a pas à adopter les chemins `crates/` et `products/` de Feluqa.

### Package du framework

Dans un item de la crate, par exemple `crates/core/feluqa-core/src/lib.rs` :

```rust
#[feluqa(kind = "crate")]
pub struct FeluqaPackage;
```

Son `feluqa.toml` est à côté du `Cargo.toml` de `feluqa-core`.

### Package module

Dans `modules/inventory/src/main.rs` :

```rust
#[feluqa(kind = "module")]
fn main() {}
```

Son `feluqa.toml` est à côté du `Cargo.toml` du module.

`tools/feluqa-build` n’utilise aucun de ces deux kinds et n’a donc pas besoin de l’attribut.

## Vérification à la compilation

L’attribut peut appeler un validateur au moment de la compilation. Ce validateur lit `feluqa.toml` à la racine du package, vérifie son contenu imbriqué et contrôle les relations entre les champs. `syn` sert à lire `kind`; il faut un parseur TOML et une validation dédiée pour le fichier.

Je garderais `version` dans Cargo. Le champ `git` du workspace peut désigner le dépôt source. Je ne garderais `tree = "1.x.x"` que si on définit exactement ce que `tree` signifie pour l’outil de split. La compilation de `feluqa-build` seule ne nécessite pas `feluqa.toml`; le contrôle s’applique aux packages marqués `crate` ou `module`.

DEfinitions des paths de storage

Avec SQLite inclus, je fixerais cette règle pour Feluqa :

- **TOML** pour le manifest et les réglages de déploiement modifiés rarement, par exemple `feluqa.toml`.
- **SQLite** pour les réglages modifiables dans l’interface, l’état persistant du module et les données métier qui changent pendant l’exécution.
- **JSON** pour les échanges, les API, les réponses CLI structurées et les documents exportés.
- **Mémoire** pour l’état temporaire qui n’a pas besoin de survivre à un redémarrage.

Une valeur modifiée dans l’interface ne devrait donc généralement pas réécrire le fichier TOML. L’application enregistre le changement dans SQLite, valide la transaction, puis applique la nouvelle valeur au runtime. Pour les réglages structurés, on peut utiliser des colonnes typées ou du JSON validé selon le besoin ; les données métier importantes et recherchées méritent un schéma relationnel.

Règles pratiques : migrations versionnées, transactions pour les changements liés, sauvegardes cohérentes, validation côté serveur et autorisation à chaque mutation. La synchronisation entre plusieurs appareils reste une règle distincte à définir : SQLite local ne la fournit pas à lui seul.



Je vais vérifier comment Zed décrit son stockage, puis comparer ça aux choix pratiques pour les applis Feluqa déployées.

Oui, **SQLite peut servir de stockage aux applis Feluqa**, comme Zed l’utilise pour certaines données locales. Mais le choix dépend de l’endroit où tourne l’application et de son usage.

Zed sépare plusieurs types de données : ses réglages utilisateur sont dans des fichiers JSON avec commentaires, tandis que les données d’espace de travail — projets récents, onglets et panneaux — sont conservées dans des bases SQLite dans son répertoire de données utilisateur. [Documentation Zed sur les réglages](https://zed.dev/docs/configuring-zed) · [Documentation Zed sur les bases de données d’espace de travail](https://zed.dev/docs/troubleshooting)

Pour Feluqa, je suivrais cette règle :

- **Appli hébergée sur un serveur** : PostgreSQL pour les données métier partagées entre utilisateurs. SQLite peut convenir à une petite installation sur un seul serveur, si les accès simultanés et le besoin de disponibilité restent modestes.
- **Appli locale sur un poste de travail** : SQLite dans le répertoire de données de l’utilisateur, avec migrations et sauvegardes.
- **Interface web dans le navigateur** : le serveur reste la source de vérité. Le navigateur peut garder des préférences simples en `localStorage` et des données locales plus structurées dans IndexedDB, notamment pour un mode hors ligne. Ces données restent propres à ce navigateur et ne remplacent pas la base serveur. [MDN : stockage côté client](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Client-side_APIs/Client-side_storage)

Donc, le modèle ressemble à Zed : **fichiers de configuration pour les réglages éditables, base de données pour l’état persistant**, et un emplacement appartenant à l’utilisateur. Pour Feluqa, SQLite est un bon choix par défaut en local ; PostgreSQL est le choix naturel pour une application hébergée et multiutilisateur. Il faudra préciser les critères exacts de bascule dans l’architecture Feluqa.
