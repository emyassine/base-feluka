Voici le document de synthèse architecturale consolidé et formalisé, conçu pour être transmis à **Codex** (ou documenté dans votre base de connaissances interne pour vos futurs travaux sur **Feluqa**).

Il formalise la stratégie de méta-programmation à la compilation (Compile-Time Metaprogramming - CTMP) en Rust pour sécuriser et intégrer la logique de licence nativement dans les binaires multi-plateformes (Web, Desktop, Mobile), tout en répondant aux contraintes physiques et de sécurité de chaque environnement.

---

## 1. Executive Summary & Core Objective

The objective is to embed licensing enforcement, cryptographic verification tokens, and conditional compilation logic directly into the static compilation pipeline of **Feluqa** (Rust-based application platform and CLI toolchain). By shifting the license verification boundary from runtime file reading to compile-time AST (Abstract Syntax Tree) transformation and binary embedding, Feluqa eliminates external plain-text configuration vectors and ensures robust multi-platform posture across **Web (Wasm)**, **Desktop (Native)**, and **Mobile (iOS/Android)** targets.

---

## 2. Technical Feasibility & Runtime Constraints Analysis

Attempting true **runtime code modification or recompilation** (dynamic generation of native machine code on the fly) is fundamentally unviable across modern target environments:

* **Web (Wasm):** Strict browser security policies prohibit executing newly allocated executable memory blocks (no `mmap` with `EXEC` permissions).
* **Mobile (iOS / Android):** Operating system security policies (W^X - Write XOR Execute) strictly reject runtime code generation or dynamic execution payloads to prevent arbitrary code injection.
* **Desktop (Windows/Linux/macOS):** Technically possible via low-level memory allocation, but triggers immediate heuristics in endpoint protection software (antivirus/EDR) as malware-like behavior (packers/droppers).

**Resolution:** Feluqa bypasses runtime recompilation entirely by leveraging **Compile-Time Metaprogramming (CTMP)** using Rust’s native build scripts (`build.rs`), procedural macros (`proc_macro`), and asymmetric cryptography.

## 3. Multi-Target Architectural Matrix

| Target Platform | Output Format | Metaprogramming Mechanism | Security Posture & Hardening Strategy |
| --- | --- | --- | --- |
| **Web (Wasm)** | WebAssembly module | Conditional macro compilation (`#[cfg]` or custom attributes) that strips/omits premium code blocks if license proofs are absent. | Because Wasm can be decompiled into text representations, **omitting the code entirely** at compile time is mandatory. Core sensitive features must not exist in the public Wasm binary without server-mediated capability flags. |
| **Desktop** | Native Executable (`.exe`, ELF, Mach-O) | Build scripts (`build.rs`) inject cryptographic byte arrays into the `.rodata` segment via `include_bytes!` or environment variables. | Relies on public-key cryptographic handshakes at startup. Hardened via LLVM-level obfuscation profiles, symbol stripping, and optional hardware-ID node-locking. |
| **Mobile** | Static/Dynamic Libraries (`.a`, `.so`, Frameworks) | FFI bridges (e.g., UniFFI) interfacing with the isolated Rust core containing the embedded verification routines. | Integrates natively with platform-specific secure receipt validation (Apple App Store / Google Play billing APIs) while keeping business core locked in the Rust boundary. |

## 4. Implementation Blueprint (The CTMP Pipeline)

```
[ Private Key (Server) ] ---> Signs Customer License Token (.lic)
                                          |
                                          v
[ CI/CD Pipeline / Build ] ---> build.rs reads token -> Validates & Encrypts -> Injects via cargo:rustc-env
                                          |
                                          v
[ Proc Macros / Core ]      ---> Embeds Ed25519 Public Key & Conditional Compilation Gates
                                          |
                                          v
[ Target Artifacts ]        ---> [ Web (Wasm) ]   [ Desktop (Native) ]   [ Mobile (FFI) ]

```

### Phase 1: Build-Time Ingestion (`build.rs`)

* The CI/CD pipeline supplies a signed license token or entitlement profile during compilation.
* The `build.rs` script intercepts this token, validates its cryptographic structure against a local public key, and converts it into a hardcoded raw byte array (`[u8; N]`), exposing it to the compiler via `println!("cargo:rustc-env=FELUQA_LICENSE_BLOB={:?}", bytes);`.

### Phase 2: Procedural Macros & Conditional Code Generation

* Custom attribute macros (e.g., `#[feluqa_guard("enterprise_module")]`) evaluate feature availability at compile time.
* If the target tier does not match, the macro strips the function body or replaces it with a stub, preventing the commercial code from ever existing in the compiled binary for unauthorized tiers.

### Phase 3: Cryptographic Verification Core

* A lightweight, zero-dependency cryptographic library (`ed25519-dalek` or `ring`) is embedded into the core.
* At application boot, the runtime evaluates the embedded signature against the hardcoded public key to establish software legitimacy before initializing critical runtime subsystems.

## 5. Threat Model & Strategic Trade-offs

1. **Static vs. Dynamic Distribution:**
* *Per-customer compilation:* Baking a unique user's license directly into a customized binary requires automated CI/CD generation pipelines (standard practice for high-value enterprise distribution).
* *Generic cryptographic validation:* Embedding a master public key to verify external signed license files allows a single unified binary to validate arbitrary user keys offline.


2. **The Reverse-Engineering Reality:**
* No offline binary verification scheme is entirely immune to a determined attacker using advanced reverse-engineering tools (e.g., Ghidra, IDA Pro) to patch boolean checks.
* *Mitigation:* For web and high-security services, offline checks serve as a frictionless first layer, while true high-tier capabilities require asynchronous server-side synchronization.
