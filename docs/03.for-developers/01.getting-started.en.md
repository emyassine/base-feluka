## Start against the current checkout

Read the [baseline](../01.introduction/01.platform-overview.en.md), then inspect
CLI help from the repository root:

```sh
cargo run --manifest-path _crates/Cargo.toml -p feluqa-cli -- help
```

This is an invocation reference, not a claim that this migration rebuilt the CLI.
Use [the command reference](../05.reference/01.cli-commands.en.md) for current
syntax. Module composition is static. Keep source under its owning domain and
follow the strict [Rust standard](../05.reference/03.rust-coding-standard.en.md).
The automatic attribute-driven app wiring is a target, not a replacement workflow
available today. External scaffolds still depend on a compatible private release.

The retained introduction below predates System-panel removal. Use generic
product panels; do not infer an available built-in administration product.

# For module developers

Feluqa supplies the platform runtime, System panel, panel framework and shared
security contracts. A module declares business capabilities and registers
them with Feluqa; it does not ship a second server or a copy of the panel.

Recommended path:

1. [Develop a Feluqa module](02.develop-a-module.en.md)
2. [Add a panel resource and page](03.panels-resources-and-pages.en.md)
3. [Store data and run migrations](06.data-and-migrations.en.md)
4. [Authorize users and actions](07.authorization.en.md)
5. [Write views and components](04.views-and-components.en.md)
6. [Add custom routes](05.custom-routes.en.md) when CRUD is not enough
7. [Test and release a module](08.testing-and-release.en.md)

The runtime currently composes modules statically into a compiled product.
System-panel installation, domain-scoped activation and license enforcement
are target capabilities, not shipped functionality. See [the module lifecycle
status](../reference/../for-developers/panels-resources-and-pages.en.md).
