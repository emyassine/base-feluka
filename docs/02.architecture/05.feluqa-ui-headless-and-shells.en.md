# Feluqa UI architecture

## Product direction

Feluqa owns the application framework and UI system across web, workstation,
mobile and constrained products. Modules use Feluqa components, themes,
navigation, forms, storage and product adapters through the readable
`feluqa::ui::*` hierarchy. They should not need to adopt a separate UI
framework for each product target.

The web panel is moving from its legacy legacy panel implementation-derived markup and assets to
Feluqa-owned components. Keep existing routes, services, authorization, CSRF,
audit handling and business logic as server-side authorities during this
migration. A hidden/disabled action is never a substitute for authorization.

## First-party source ownership

Adapted component source is maintained in Feluqa workspace packages, not
consumed from an upstream registry or a nested `vendor/` path:

- `feluqa-ui-components`: components, blocks, charts, hooks and utilities.
- `feluqa-ui-component-macros`: component composition macros.
- `feluqa-ui-classnames` and `feluqa-ui-classnames-macros`: class merging and
  typed variants, under Feluqa names.
- `feluqa-ui-autoform`: form derive source.
- `feluqa::ui::icons`: icon components inside the Feluqa UI namespace.

Provenance and required third-party notices are kept in
`_crates/feluqa-ui-components/NOTICE-RUST-UI.md` and with the relevant source.
Public application code should use Feluqa namespaces such as
`feluqa::ui::component`, `feluqa::ui::block`, `feluqa::ui::hook` and
`feluqa::ui::icons`.

The no_std SDUI schema and renderer remain independent of browser rendering.
The current component implementation still has an external rendering-runtime
dependency; the runtime itself is not yet a Feluqa-owned implementation. Do
not confuse internalized component packages with completion of the runtime
fork or the product build integration.

## Panel migration sequence

1. Compile the first-party components under Feluqa's strict Rust settings and
   establish the product feature/MSRV boundary.
2. Integrate server rendering and hydration with the existing Axum web product
   and its asset pipeline.
3. Build one shared Feluqa panel sidebar/layout block that supports the
   supplied navigation view, active links, persisted open/collapsed state,
   desktop variants and mobile sheet behavior.
4. Migrate the System panel shell and `/system/modules`, then Overview and
   Users. Preserve current permission checks, handlers, forms, CSRF and audit
   behavior.
5. Use the shared layout across System, application-admin and business panels;
   retain each panel's navigation content and allow product-owned custom
   sidebars through the Feluqa component API.
6. Inventory all current panel pages and interactions. Migrate forms, tables,
   notifications, dialogs, widgets, theme switching and language selection.
7. Compare authenticated routes at desktop/mobile widths in light/dark themes.
   Verify keyboard and screen-reader behavior, submissions and server-side
   authorization.
8. Remove legacy panel assets and compatibility classes only after route
   inventory and browser evidence show they are unused.

## Completion criteria

The migration is complete only when every panel route and interaction uses the
Feluqa component API, shared layouts cover the supported sidebar variants,
the System modules page is migrated, product builds pass from a clean checkout,
browser evidence passes, and old assets are unreferenced and removed.

Current status: first-party source has been moved and renamed, but it does not
yet compile cleanly. Product integration, runtime ownership, SSR/hydration,
System panel migration, responsive/theme verification and legacy asset removal
are not complete.
