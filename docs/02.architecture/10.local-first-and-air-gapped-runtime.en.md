# Local and disconnected Feluqa products

**Status:** selected product direction; runtime and security designs remain to
be implemented. This chapter records the local use cases and architecture
requirements the owner set on 2026-10-28. See the [implementation baseline](../01.introduction/01.platform-overview.en.md)
and [remaining decisions](../decisions/01.pending-decisions.en.md).

## Who Feluqa must support

Feluqa serves two different operating contexts:

| Context | Product need | Target deployment |
|---|---|---|
| Sensitive or regulated work, including military, medical, laboratory and restricted sites | Keep data, keys and operations under local organizational control. Continue when Internet and central services are unavailable. | A local Feluqa server on an approved computer or server, with no required remote service. Devices use a local network or connect directly to the host. |
| Small businesses, shops, services and independent operators | Start with little administration. Keep working when the Internet is unavailable. Let nearby devices use the same business data. | One computer acts as a local server. Other computers, tablets or phones connect over the local network using a browser or supported application. |

A product can also run as a hosted web service. The same module source must
support the hosted and local products without duplicating its business rules.

These are product requirements. They do not claim that Feluqa meets a legal,
medical, military or safety certification.

## Local server and client model

A Feluqa instance must be able to run a lightweight server on a supported node,
such as a workstation, laptop or approved server. A client on the same network
can connect directly to that server through a browser or a supported native
shell. The local workflow must not require Internet access, a cloud service or
an external identity provider.

Keep the Rust business logic and module contracts shared across products.
Compile them for each supported target, and add target-specific storage,
network and user-interface adapters. A web server can provide local browser
access. A desktop or mobile application can use an approved local shell. These
adapters are separate runtime pieces; “one module source” does not mean one
binary runs unchanged on every device.

A local server is the selected initial network shape. The proposal also mentions
peer-to-peer operation. Direct device-to-device synchronization without a host
is still an open design choice. Do not describe it as supported until a separate
architecture and recovery plan exist.

## Disconnected operation

The base product must run without contacting a content-delivery network (CDN),
cloud control plane or third-party application programming interface (API).
Bundle required interface assets with the product or serve them from the local
host. Make outbound connections an explicit, configured integration.

A disconnected installation needs an offline path to install and update the
platform and modules. Verify imported packages and signatures locally. Keep
local data, identity, authorization and audit available when the site is isolated.
Do not require a daily Internet check for the system to continue its local work.

Local clients can reach their host while they share a network. If devices become
separated, the product must define which operations can continue on each device
and how their changes return to the host. Multi-device offline writes and conflict
resolution require a chosen policy for each data type. The product goal is
resilience to network loss; a particular conflict algorithm has not been selected.

## Local identity and sensitive data

Administrators must control the local trust anchors and keys for a disconnected
installation. Device enrollment and revocation must work without a remote service.
Require authenticated users and devices, least-privilege access and an audit
record for sensitive actions.

Sensitive deployments require a documented threat model, local key custody,
protected network transport and end-to-end protection for data that must remain
unreadable to intermediate nodes. Mutual Transport Layer Security (mTLS) can
authenticate a connection; a decentralized identifier (DID) can identify a
principal; end-to-end encryption protects data across intermediaries. These
mechanisms serve different roles. The exact protocol, key lifecycle and trust
model remain open.

Require human approval for sensitive agent actions, such as approving a medical
recommendation or sending operational telemetry. Use local permissions and an
audit trail. The owner has not yet selected the exact action categories,
credentials, approval roles or emergency override policy.

## Storage and packaging

Use the same domain rules and module contracts in hosted and local products.
Select storage engines through profile adapters. SQLite, RocksDB and sled are
candidates from the product discussion; this chapter does not select among them
or promise that each works on every target. Define backup, restore, migration
and recovery for each supported local configuration.

The WebAssembly Component Model remains the default target artifact for
installable modules in the platform architecture. Native products still need
compatible builds or runtimes for their targets. Record package versions,
platform compatibility, publisher trust and signatures so an operator can
verify an update before importing it into an isolated installation.

## Acceptance evidence

Before claiming local or disconnected support, demonstrate that:

- One module builds into a hosted web product and a local workstation product.
- A workstation or small server hosts the app, and nearby clients use it over a
  local network with Internet access disabled.
- Required assets, identity, storage and module installation work in an isolated
  environment.
- Administrators can enroll and revoke devices and manage trust anchors locally.
- Sensitive actions require the configured approval and produce an audit record.
- The product documents its storage, backup, restore and offline update process.
- Network loss and recovery tests show what happens to reads, writes and
  concurrent changes. Results match the selected per-data-type policy.
