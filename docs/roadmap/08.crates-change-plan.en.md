# Planned changes to `_crates/`

[Target] This plan moves `_crates/` toward the selected architecture in the [Monorepo Architecture](../02.architecture/01.monorepo-architecture.en.md), [Product Document](../01.introduction/02.intent.en.md), and [Compilation requirements](../02.architecture/02.compilation-and-targets.en.md). I reviewed the manifests on 2026-10-28. I did not rerun build acceptance. See [current status](../01.introduction/01.platform-overview.en.md) and [open decisions](../decisions/01.pending-decisions.en.md).

## Current workspace

`_crates/Cargo.toml` currently sets resolver 3, edition 2024 and Rust 1.85. Some UI packages require Rust 1.88. The facade enables the web feature by default. The target architecture moves Cargo to the repository root, groups packages under `crates/`, and moves native shells outside the Cargo workspace. It also adds a pinned toolchain and dependency policy. Review compiler and package compatibility before you select exact versions. The existing Core, definitions, facade, UI packages and product breakage are migration inputs.

## Workspace and package migration sequence

The root workspace move and domain grouping are selected target architecture.
Implement them as a staged repository migration: enumerate every member, path
dependency, patch and product; establish root workspace/package policy and pinned
toolchain; move packages by owner domain while preserving package names and public
`feluqa::...` facade; then update products, CLI context discovery, watcher roots,
release scripts, registry metadata, crate docs and commands. Move Swift/Kotlin/GTK/Qt/WinUI
shell projects outside Cargo under `shells/`. Keep lockfile resolution reproducible
and retain current private-registry restrictions.

Do not mechanically rename crates just to match the diagram. First map each existing
package to its target responsibility, split or combine only where needed, and keep
provenance/notices with adapted code. Preserve identity persistence and database
schemas across the migration. Add useful contracts and consumers before adding a
package; never create empty crates to match the diagram. `feluqa-core`/`feluqa-nostd`,
bridge crates, agent/deploy services and target runtimes are target architecture
items whose concrete implementation and acceptance must be sequenced.

Resolve workspace compiler edition/resolver and UI MSRV compatibility in the root
manifest/toolchain lane before raising any crate requirement. The architecture example
is a target template, not a tested lockfile or blanket dependency approval. Keep
Tokio and other server dependencies out of kernel/real-time crates.

## Verification gates

Run scoped tests while implementing, then the repository's required checks:

```sh
cargo fmt --manifest-path _crates/Cargo.toml --all --check
cargo check --manifest-path _crates/Cargo.toml --workspace --all-targets --locked
cargo clippy --manifest-path _crates/Cargo.toml --workspace --all-targets --locked -- -D warnings
cargo test --manifest-path _crates/Cargo.toml --workspace --locked
```

Add declared MSRV and non-web/feature-specific builds, compiler negative cases,
filesystem containment/symlink tests, tenant/authorization denial and browser
acceptance where the work touches those boundaries. A newer compiler passing
cannot establish MSRV. Record toolchain, commands, results, remaining failures
and representative consumer for each work package; estimates follow the spike.

This documentation change updates only an existing dependency-policy link inside
`_crates/`; it does not modify Rust, Cargo configuration, lockfiles or runtime code.
