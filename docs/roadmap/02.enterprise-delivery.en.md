# Enterprise delivery plan

This plan defines the remaining delivery tracks, rough engineering effort and
acceptance evidence. Estimates are person-days for an experienced Rust
engineer, including review and verification; they are planning ranges, not
dates or a commercial quote. Parallel work and external deployment access may
change calendar time. `exists/` describes what has actually been verified.

## Delivery tracks and estimates

| Track | Rough effort | Current gap and acceptance evidence |
|---|---:|---|
| F0. Webkernel language/component inventory and shared conformance fixtures | 3–5 days | Complete the directive/component matrix and connect compiler, Tree-sitter and editor fixtures. |
| F1. `.view.rs` compiler | 10–16 days | Initial compiler exists; finish the grammar contract, diagnostics and conformance checks across build profiles. |
| F2. Tree-sitter and Zed | 6–10 days | Grammar/package generation exist and a representative parser smoke sample succeeds; port stateful HTML tag matching/recovery, add shared compiler/grammar fixtures, then install in a pinned Zed release and verify suffix detection, injections, highlighting and recovery. Global IDE CLI commands are estimated separately at 2–4 days. |
| F3. Components and SDUI | 12–20 days | Initial schema and renderer exist; add typed props/slots, accessible forms, theme APIs and browser-tested behavior. |
| F4. Data, Core and panels | 15–25 days | Database, auth and vertical panel slices exist; finish generic resources/actions, tenant lifecycle, PostgreSQL HTTP coverage and restore. |
| F5. Live actions | 10–18 days | Signed typed dispatch exists; add shared replay protection, client reconciliation/focus handling and failure/reconnect tests. |
| F6. Sites, CLI and deployment | 8–14 days | Local scaffold/watcher exist; validate standalone builds, a second independent site, production deployment and rollback. |
| F7. Installable module lifecycle | 12–20 days | Static lifecycle exists; implement artifact compatibility/signatures, licensing, domain activation, staging, recovery and safe uninstall/data retention. |
| F8. Feluqa UI and panel migration | Unestimated pending build spike | Internalize the component source as first-party Feluqa packages and namespaces, integrate rendering/hydration with Axum, migrate all panel pages/interactions, verify light/dark and responsive behavior, then remove unused legacy assets. Acceptance is in [the Feluqa UI architecture](../02.architecture/05.feluqa-ui-headless-and-shells.en.md). |
| F10. Feluqa-owned UI runtime | Unestimated | Replace the remaining external rendering-runtime dependency with a first-party maintained runtime under Feluqa namespaces, or implement the required compiler/runtime surface directly. Preserve web SSR/hydration, workstation/mobile outputs and the no_std boundary. Do not call the current component-source copy a complete runtime internalization. |
| F9. One module, web and workstation products | Unestimated architecture and prototype | Make one business module deployable as a hosted web application or a standalone workstation application. Define shared domain/application logic and separate web, desktop, storage and connection adapters. For the bookstore scenario, the same books, sales, stock and student-facing behavior must support a public website with business administration and a local-only workstation installation. Then design optional multi-device sessions over a local peer network or a routed connection, with explicit identity, authorization, synchronization, conflict handling, offline behavior, backup and recovery. No desktop framework, synchronization protocol, or database topology is selected yet. See [the web and workstation module plan](05.web-and-workstation-modules.en.md). |
| F11. Attribute-driven application scanner | Unestimated | Initial scanner foundation exists: conventional source discovery, context from module directories, basic duplicate/reference checks, permission/role docs and write-handler gate checks; Numerimondes emits a declaration inventory. Complete attribute validation, recursive inline-module context, runtime/code generation for routes/permissions/configs and generated docs/examples; keep generated output deterministic under `target/feluqa/`. See [the attribute-driven application contract](../02.architecture/03.attribute-driven-applications.en.md). |
| F12. Declarative panel, resource and gate APIs | Unestimated | Add `#[feluqa::main]`, `#[panel]`, `#[resource]`, `#[page]`, `#[permissions]`, `#[roles]`, `#[config]` and `#[gate]` contracts. Generate panel-relative slugs, resource CRUD routes/pages/navigation/permissions, typed permission references, secure-by-default write gates and shared privilege-management resources. Migrate Numerimondes and remove its manual route, provider and registry declarations without changing business behavior or `feluqa/imagery`. |

These tracks have dependencies and some can run in parallel. Do not sum the
ranges as a committed schedule; re-estimate after each acceptance gate exposes
the actual integration work.

The global `feluqa support:ide ...` command family and its context rules are
specified in the [IDE support plan](06.ide-support-commands.en.md). These
commands are available regardless of app/module/workspace context; they are
not implemented yet.

## Release gates

- **Platform module lifecycle:** signed package compatibility, license and
  permission checks, per-domain activation, staged upgrade/recovery, disable
  and explicit data-retention behavior.
- **Module developer experience:** concise providers, panels, resources, pages,
  clusters, widgets, CRUD adapters, migrations, seeders and standalone builds.
- **Enterprise panels:** complete Feluqa theme/component system,
  accessible forms/tables/actions/notifications, responsive Core panel and
  first-class public-site panel composition; see F8. legacy panel implementation parity is no
  longer the target.
- **Security and data:** server-side authorization on every action,
  tenant/record isolation, PostgreSQL HTTP coverage, audit and a verified
  restore drill.
- **Operations:** production deployment, graceful shutdown, observability,
  backup/restore runbooks and security/documentation review.
- **Cross-surface delivery:** a representative module builds for hosted web and
  standalone workstation from one module codebase. Multi-device access is
  enabled only after its trust, sync, offline, conflict and recovery model has
  end-to-end evidence.
- **Application composition:** source attributes and conventional module
  paths are the only maintained declaration source; no handwritten route,
  permission, resource, provider or config registry remains in the product.

Do not call the platform enterprise-ready until each applicable gate has an
end-to-end application test and operational evidence.
