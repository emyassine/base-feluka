## At a glance

- **Feluqa is now one ecosystem and one namespace for web, SPAs, mobile, desktop, games, APIs and real-time systems.** Unifying tooling, schemas, libraries and naming is achievable. Unifying the runtime is not: a web server (sub-millisecond latency), a game (16.6 ms frames) and a flight controller (hard deadlines, no garbage collector) have opposite constraints. The design answer is one workspace with target profiles (A1b).
- **Fixed exclusions:** PHP, C#/.NET, JVM languages, and C++ as a host. They are owner decisions, recorded as such.
- **The language decision now depends on scope.** If the real-time profile stays in scope, only Rust covers every target in one language: Go's garbage collector and runtime rule it out for control loops. If scope narrows to web, APIs and desktop, Go stays competitive. Rust leads today.
- **Your four questions are answered in Part B:** Go's nil and error boilerplate against Rust's Option, Result and trait boilerplate (with code); dependencies you can see, vendor and rename; and ecosystem maturity by target.
- **Copying existing frameworks is limited by verification, not typing.** With AI agents, the cost of a port is whether a test suite proves it. Choose sources that have one, and test ports black-box.
- **Military and drone use adds legal and assurance work, not only code.** In release 1 Feluqa's role is ground-side (mission planning UI, telemetry, fleet APIs). Certified flight software is out of scope, but the kernel crates must keep that door open.
- **Planning is gated by criteria, never by dates.** This document contains no durations; every milestone passes on measured results.
- **Under 1 ms applies to the server profile,** and only with embedded SQLite and caching.

## Part A — Product requirements and developer experience

### A1. Goal and fixed constraints

Feluqa is a compiled application platform with one ecosystem and one namespace for web, SPAs, mobile apps, desktop apps, games, APIs and real-time systems (A1b). The first profile to ship is the server profile: a single native binary for Linux. **Fixed constraints (Accepted):**

1. Compiled native code only. No PHP at any layer: no PHP interpreter, no PHP bridge, no Composer packages at runtime.
2. No Microsoft stack: no C#/.NET as host or runtime language (owner decision, D-0021).
3. No JVM languages: no Java, no Kotlin on the JVM (owner decision, D-0021).
4. Webkernel is a source of ideas and a migration source, never a runtime dependency.
5. Everything in Part A must hold whichever language wins in Part B.

With no module installed, Feluqa provides: an HTTP/TLS server and router; an embedded database by default; a **built-in system panel ("Feluqa Core")** in the spirit of PocketBase, with superadmin, roles and ACL; a view language, schema-driven UI (SDUI) and live components; a CLI with a fast development loop; and hosting for **static, partially dynamic and fully dynamic** sites from the same project layout.

It deploys in two situations: behind an existing panel (Hestia first; other panels later and uncertain), or managing a whole server (edge, apps, services). Existing panels stay supported.

**Performance goal:** a representative complex request (session, authorization, several queries, HTML render) takes under 1 ms at the median, server-side.

**Non-goals for release 1:** billing, centralized hosting/fleet administration across unrelated servers, DNS management, a public module marketplace, phpMyAdmin/pgAdmin replacements, Windows production support. Feluqa System must still manage modules and licensed capabilities for domains hosted by that Feluqa installation; that is platform module management, not a public marketplace or cross-server hosting product.

**Critique.** "Complete platform" and "1 ms" pull against each other: every built-in feature on the hot path costs microseconds. The discipline is that each feature declares its hot-path cost and is benchmarked in CI against the reference scenario (A2). The current `__rust/first-demo` is only an HTTP deployment probe and implements none of this.

### A1b. One ecosystem, several target profiles

Feluqa is one ecosystem: one workspace, one namespace, one CLI, one schema and policy model, one module system. It is not one runtime. Each target gets a profile with its own runtime model. Shared crates (schemas, policies, protocols, validation, serialization) compile into the compatible profiles, and one facade (`feluqa::...`) exposes them under a single name. The current facade feature sets are `web` (default), `spa`, `mobile`, `desktop`, `game` and `realtime`; `cargo check -p feluqa --no-default-features --features realtime` validates only the no_std host build, not an embedded target or hard-deadline guarantee.

Exhibit 1b | Target profiles and their binding constraints

| Profile | Targets | Binding constraint | Runtime model | Consequence for the language |
| --- | --- | --- | --- | --- |
| Server | Web back ends, APIs | p50 under 1 ms per request (A2) | Native binary, async I/O, embedded SQLite | Fast native code; GC pauses hurt p99 |
| Web client | SPAs | Bundle size, load time | WebAssembly or generated JavaScript from the same schemas | Needs a WebAssembly target |
| Desktop | Linux, macOS, Windows | Installers, auto-update, code signing | Webview shell or native UI toolkit | Mature cross-platform UI frameworks |
| Mobile | iOS, Android | Battery, app-store rules, platform UI | Shared core library plus platform UI, or a cross-platform toolkit | C-compatible FFI, small binaries |
| Games | 2D and 3D | 16.6 ms frame budget at 60 fps, deterministic simulation | Entity-component-system, GPU rendering | No GC pauses; data-oriented code |
| Real-time and embedded | Ground stations, flight-adjacent software, devices | Hard deadlines, bounded memory, no heap allocation in control loops | `no_std` libraries on an RTOS or bare metal | No garbage collector, no mandatory runtime |

**Critique: one namespace, not one runtime.** Putting a web server and a flight controller in one process would break both. The promise is shared contracts, tooling and naming, with a separate runtime per profile. Anything stronger is marketing.

### A1c. Feluqa platform and installable modules

Feluqa is the installed host platform; its built-in System panel manages
modules for domains. Modules contribute capabilities through Feluqa APIs and
are subject to compatibility, license and permission checks. Runtime
installation, domain activation and license enforcement remain unfinished;
registration is static and compiled today. For package shapes, vocabulary and
the target lifecycle, see [platform and module layout](../02.architecture/06.platform-module-layout.en.md).

**Critique: mobile and downloadable modules.** App stores restrict code downloaded and executed at run time, so runtime modules (D-0005) may be limited on iOS. Verify the current store rules before promising it; the fallback is compile-time modules delivered through store updates.

**Critique: scope against capacity.** Six profiles on top of the platform itself is a large commitment. Each profile starts only when the previous profile's gate has passed (C1), and the server profile is first.

**Critique: SPAs.** A single-page app compiled to WebAssembly ships larger bundles than hand-tuned JavaScript. Most pages should stay server-driven (A9); the SPA profile is for applications that need client-owned state.

#### Real-time, safety-critical and defense use (Proposed boundaries)

In release 1, Feluqa's role in defense and drone contexts is **ground-side software**: mission-planning and monitoring interfaces, telemetry ingestion, fleet and asset APIs, logging, simulation tooling, and data-link protocols such as MAVLink. Certified flight-control software is out of scope for release 1. Flight-critical code needs certification evidence (DO-178C for airborne software, MIL-STD-882E for system safety, STANAG 4671 and 4586 in NATO contexts, IEC 61508 as a generic base), a qualified toolchain, hardware-in-the-loop testing and a safety case. Mature open flight stacks already exist (PX4, ArduPilot); interfacing with them over MAVLink is cheaper than rewriting them, and it avoids embedding GPL-licensed code (check each project's current license).

Design constraints that keep the door open from day one:

1. Kernel crates (types, protocols, schemas, policies) are `no_std`-capable, with no hidden allocation and no panics on valid input.
2. The real-time profile uses no garbage-collected language.
3. Builds are deterministic, with a pinned toolchain.
4. Every dependency in the real-time profile is vendored and reviewed.
5. No WebAssembly or dynamic loading inside a control loop.

**Critique: military use has legal consequences.** Export-control classification (EU Dual-Use Regulation, US EAR and ITAR), customer screening and licensing apply to the product and to its marketing. Get specialist counsel before positioning Feluqa for defense. Feluqa is proprietary; proprietary ownership does not change third-party component licenses or export obligations.

### A2. Performance contract

**Definition.** "Under 1 ms" means p50 server-side handling time, measured at the application socket (excluding network, TLS handshake and any front proxy), on one core, warm, on the reference scenario. A p99 target (proposed: under 5 ms) is tracked beside it.

**Reference scenario.** `GET /orders/{id}`: validate session; authorize (role plus row-level); three indexed queries (the order; 20 line items with a join; the customer); render a full HTML page with layout and a 20-row table; database of about 1M rows; no on-the-fly compression of the response.

| Step | Budget (estimate) | Notes |
| --- | --- | --- |
| Front proxy to Unix socket | 100–300 µs | Outside the definition but felt by users. Prefer Unix sockets. |
| HTTP parse + routing | 10–30 µs |  |
| Session + authorization | 5–50 µs | Cached session, in-process policy evaluation. |
| Database | 50–600 µs | Embedded SQLite, prepared statements: 10–100 µs per indexed query. MySQL/PostgreSQL on loopback: 150–500 µs **per round trip**. |
| Render | 20–300 µs | Compiled templates; a 50-row SDUI table is at the high end. |
| Module call on the path | 10–100 µs | Pooled instances, bounded host calls. |
| Response write | 5–20 µs | Never compress dynamic responses on the hot path. |

**Rules that follow:**

1. Embedded SQLite is the default database; MySQL/PostgreSQL are optional and only meet the goal with very few round trips.
2. No reflection-heavy data mapping on the hot path: generated or typed queries and prepared statements.
3. Templates, schemas and expressions compile at build or deploy time, never per request.
4. No module instantiation per request; pooled instances only; hot-path modules declare a time budget.
5. A CI benchmark runs the reference scenario and fails the build on regression.
6. Row-level ACL is pushed down into the SQL `WHERE` clause, never filtered in application memory.

**Critique.** SQLite has a single writer: excellent for read-heavy sites and admin tools, weaker for write-heavy multi-node loads. Plan replication/backup and an explicit PostgreSQL path; do not promise horizontal scaling in v1.

### A3. Rendering modes: static, cached, dynamic, live

Each route declares one mode; a project mixes them freely.

| Mode | What happens | Typical cost |
| --- | --- | --- |
| **Static** | Built at deploy time, pre-compressed, served from memory or disk with ETag. | 10–50 µs |
| **Cached** | Rendered once, then served from an in-process cache; stale-while-revalidate; invalidated by tags (a write to `orders` invalidates `tag:orders`); fragment caching for partially dynamic pages. | 20–100 µs on a hit |
| **Dynamic** | Full request: session, ACL, queries, compiled template. | under 1 ms |
| **Live** | A dynamic page whose components update through named server actions and DOM morphing. | per action, same budget |

**Critique.** Most real sites are 80% cacheable, and the cheapest request is the one that never executes. Tag-based invalidation is the hard part (correctness over speed); design it into the kernel, not as a later plugin.

### A4. Feluqa Core: the built-in system panel

Ships in the binary, works with zero modules, and is itself built with Feluqa's SDUI, so the SDUI API is tested by the product's own admin.

**Capabilities (release 1):**

- Collections/schema editor with migrations generated from schema changes, and a typed API per collection.
- Authentication: password (argon2id), OAuth2/OIDC, optional passkeys, email verification, sessions and API tokens.
- Superadmin and ACL (below).
- File storage (local disk first, S3-compatible later).
- Realtime events (server-sent events first).
- Request log, audit log, settings, backup/restore, health and metrics endpoints.
- Full CLI/API parity with the panel.

**Authorization (Proposed):**

- Deny by default. Three strictly separate scopes: **platform** (server administration), **app** (one application's admin), **end user**. A compromised app admin must never become server root.
- Coarse authorization as data-driven policies editable in the panel (a policy engine such as Cedar or Casbin).
- Row-level rules as a small expression language compiled to SQL predicates (the PocketBase "API rules" idea). A policy engine alone cannot do this, because filtering lists needs SQL pushdown.
- Audit log for every privileged action; impersonation explicit, logged and time-limited.

**Critique.** Copy PocketBase's *model*, not its admin UI: its dashboard is a client-side SPA, which contradicts Feluqa's server-driven thesis and would leave two UI stacks. Its rule system is also simple; real ACL (teams, delegated admin, per-field rules) is a design project. Write the ACL spec before the admin UI.

### A5. Developer experience

DX is a stated differentiator, so it gets requirements, not adjectives.

**A5.1 Requirements**

| Capability | Requirement | Target |
| --- | --- | --- |
| Start | `feluqa new` scaffolds a project with the Core panel and one example collection | running in under 10 s |
| Dev loop | `feluqa dev` polls app/framework sources, compiles a new binary while the current one serves, and restarts only after a successful build | under 5 s incremental (target; current polling/rebuild latency not measured) |
| Code changes | In-place restart that keeps the database and sessions | under 5 s incremental |
| Errors | Dev error page with source location, failing query and request; structured logs in production | always |
| Request inspector | Dev panel showing queries, timings, cache hits, policy decisions per request (Laravel Debugbar/Telescope idea) | built in |
| Types and IDE | Typed API and client types generated from the schema; JSON Schema for config files so editors autocomplete | generated on save |
| Migrations | Diff-generated, reviewable, reversible | one command |
| Testing | `feluqa test` with in-memory database, HTTP test client, fixtures | no setup |
| Build and deploy | `feluqa build` produces one artifact; `feluqa deploy` swaps it with zero downtime | one command each |
| Module authoring | `feluqa module new` scaffolds a module in each supported SDK language | one command |
| Onboarding | A developer who knows Laravel builds a working CRUD app with auth and ACL | under 1 hour |

**A5.2 The unresolved question: how do developers write application logic?**

A compiled platform changes what "writing the app" means. Three authoring models:

| Model | App logic lives in | Strength | Weakness |
| --- | --- | --- | --- |
| 1. Host-language code | Code in the platform's own language, compiled with Feluqa | Fastest runtime, full type safety | Slower edit loop; app developers must know that language |
| 2. Declarative + compiled modules | Schemas, views, policies cover most needs; hard logic in WASM modules (any language) | Language freedom, sandboxed | Module ABI must be excellent; more moving parts |
| 3. Declarative + embedded scripts | Schemas, views, policies; glue logic in a small scripting language | Instant reload, low barrier | Slower than compiled; two languages |

**Recommendation (Open):** declarative first (it should cover about 80% of a typical app), scripts for glue, compiled modules for hard or hot-path logic. Model 1 stays available for platform contributors. This choice shapes the language decision in Part B.

**Critique.** The old brief compared languages before deciding who writes the app code. If app developers write host-language code, build speed becomes a DX feature and Part B must weigh it heavily. If they write declarative configs plus scripts, host-language ergonomics matter less and runtime performance matters more.

### A6. Project layout and migration from Webkernel

A recognizable project root; `public/` is the only HTTP document root:

```text
project/
├── app/
├── config/
├── modules/
├── public/                 # only public document root
├── runtime/
├── storage/
├── feluqa.toml             # app manifest
└── package.json            # frontend assets, optional
```

For Hestia the project can live in the domain's `public_html/` with the custom document root set to `/public/` (Hestia maps this to `public_html/public/`); the executable and private metadata stay outside it.

**Migration is conversion, not compatibility.** There is no PHP runtime, so nothing PHP executes inside Feluqa.

| Webkernel asset | What happens |
| --- | --- |
| Panel and schema definitions (declarative) | Automatic converter to Feluqa schemas |
| Views (Blade-like syntax) | Converter for the supported directive subset; unsupported constructs listed in a report |
| Routes, config, environment | Automatic converter |
| Database | Import tool: existing MySQL/PostgreSQL data into the Feluqa database |
| Business logic (controllers, jobs, closures) | Rewritten by hand in the chosen authoring model; no automatic translation |
| Composer packages | No equivalent; replaced by Feluqa modules |

`feluqa migrate inspect` reports, before any conversion, what converts and what needs rewriting. "Existing configuration stays intact" is true only for the declarative subset; say so plainly to users.

### A7. Deployment models

**Existing panel adapter.** The panel owns public virtual hosts, DNS-facing HTTP/HTTPS and certificates. Feluqa registers and supervises the app on a loopback address or Unix socket; the panel's web server proxies to it.

```sh
feluqa app add \
  --dir=/home/yassine/web/rust-demo.example.com/public_html \
  --domain=rust-demo.example.com \
  --adapter=hestia
```

Without administrator privileges, the adapter validates the app and prints the exact Hestia action still required. With an explicitly installed privileged integration it uses Hestia's supported templates or CLI. It never silently patches panel-generated virtual-host files, because panels regenerate them. Hestia is the first adapter; the adapter contract must admit other panels later without changing the runtime model.

**Feluqa-managed server.** An optional server-wide installation manages the HTTP/TLS edge, apps, domains and services, with database tooling later. Caddy is a candidate edge component (automatic certificates); Feluqa provides installer, app registry, permissions, workflows and the admin interface. The Feluqa control API and any edge admin endpoint stay private. Each app gets its own OS user, a sandboxed systemd unit (filesystem protection, no new privileges, CPU/memory/task limits) and a private data directory.

**Critique.** Shared hosting on cPanel or Plesk generally forbids long-running custom processes, so Feluqa-as-a-service targets VPS and dedicated servers; "supports cPanel" is a long-term, uncertain claim. The managed-server mode is where security risk concentrates: a daemon that creates users and writes service units is root-adjacent. It needs a threat model first: a small privileged helper with a narrow API, everything else unprivileged, signed releases. Do not ship it in release 1.

### A8. Modules and extensions

**Framework modules** are versioned, testable modules linked into the binary (database drivers, panel adapters, UI kits, build tools); optional ones must not burden every installation.

**Downloadable runtime modules (Accepted).** Users can download a compatible module over HTTPS, install it and enable it **without rebuilding the host**, with safe activation and rollback. A manifest declares: ID and version; supported Feluqa API version; artifact format and target; dependencies; requested permissions; digest and publisher signature.

Lifecycle: download to staging, verify digest and signature, check compatibility and capabilities, prepare, activate atomically, route new work to the new version while in-flight work drains, keep the previous version for rollback. A failed activation leaves the prior version enabled; state migration needs an explicit contract.

| Tier | Mechanism | Use for | Isolation |
| --- | --- | --- | --- |
| 0 | Declarative: config, schema, policies, templates, expressions | Most customization | No code execution |
| 1 | Embedded scripting (JavaScript is the likely audience fit) | Hooks, validation, small automation | Sandboxed interpreter |
| 2 | WebAssembly modules | Performance-sensitive or third-party code, many source languages | Capability-based sandbox |
| 3 | Out-of-process plugin over a local socket | Heavy or legacy code | OS process boundary |

**Why WebAssembly for tier 2.** The requirement (D-0005) is that someone else's code can be installed into a running, compiled host without rebuilding it and without trusting it. A compiled host has three ways to do that. It can load a native shared library: this runs with the host's full privileges, is tied to one OS and CPU, and Go's own plugin system is unusable for it. It can run the code in another process: safe, but every call pays inter-process communication (an estimated 50–200 µs) plus process supervision. Or it can embed a virtual machine. WebAssembly is the embedded option built for this case: no ambient authority (a module can only call what the host hands it), one artifact for every CPU signed once, near-native speed (an estimated 1.2–2× slower than native), pooled instantiation in microseconds, hard memory and CPU limits, and any source language that compiles to it (Rust, C, C++, Zig, Go).

**Costs:** an ABI to design and version, marshalling on every host call, harder debugging, an immature Component Model, and no threads or sockets in guest code unless the host provides them. **It is not mandatory.** If release 1 ships only first-party modules compiled into the binary, WebAssembly can wait until M3 without breaking any requirement. It becomes necessary the day a stranger's module is installed.

**Alternatives to WebAssembly.** Eight ways to extend a compiled host, compared on the same criteria. Call costs are estimates until M0.

Exhibit 2a | Module mechanisms compared

| Option | Loads without rebuilding host? | Isolation | Call cost (est.) | Source languages | Main weakness | Fit |
| --- | --- | --- | --- | --- | --- | --- |
| Declarative only (config, policies, templates, expressions) | Yes | No code runs | Zero | n/a | Limited power | **Default; covers most needs** |
| Embedded scripting (JavaScript via a QuickJS- or goja-class engine, Lua, Starlark) | Yes, source loaded | Interpreter sandbox; weaker resource limits | 5–50 µs, slow compute | One language | Slower; interpreter bugs are host bugs | Hooks, validation, glue |
| **WebAssembly** | Yes | Capability sandbox, hard limits | 10–100 µs | Rust, C, C++, Zig, Go and more | ABI design; Component Model immature | Third-party modules on the hot path |
| Out-of-process plugin (Unix socket or gRPC, HashiCorp go-plugin style) | Yes | OS process boundary | 50–200 µs | Any | IPC cost; supervision | Heavy or legacy code off the hot path |
| Sandboxed process (Landlock, seccomp, namespaces, gVisor) | Yes | Kernel-enforced, strong | 50–200 µs | Any | Linux-only; setup complexity | Untrusted heavy workloads |
| V8-isolate runtime (workerd or deno\_core style) | Yes | Strong isolates | 20–100 µs | JavaScript, TypeScript (and WASM) | Very large dependency; memory | Only if the JS/TS ecosystem is a goal |
| Compile-time modules (custom build, Caddy's xcaddy model) | **No**: rebuild, possibly by an automated build service | None | Zero | Host language | Violates D-0005 unless a build service exists | First-party modules in release 1 |
| Native shared library (dlopen, Rust cdylib) | Yes | **None**: full host privileges | Under 1 µs | C, C++, Rust | A module crash kills the host; ABI and OS bound; unsafe unloading | Trusted first-party only, never third parties |

**Recommended layering (Proposed):** declarative first, scripts for glue, WebAssembly for third-party code that must be fast, out-of-process for heavy or legacy code, compile-time modules for first-party code in release 1. Native shared libraries are never offered to third parties. V8 isolates are rejected unless a JavaScript ecosystem becomes a product goal, because the dependency outweighs the benefit.

**WASM contract.** Start with core WebAssembly and a small, versioned ABI (or an existing plugin framework with ready SDKs); move to the Component Model/WIT once the chosen host runtime supports it reliably. The host grants capabilities explicitly (paths, network hosts, database operations) and limits CPU, memory and wall time. Never download and run source from arbitrary URLs. Native shared-library plugins are not the default: OS-specific, full host privileges, ABI and unloading problems.

**Critique.** HTTPS is transport security, not trust. The trust chain is the signature: define who holds publisher keys, how they rotate and are revoked, and how clients detect rollback and freeze attacks (use a TUF-style metadata model or Sigstore; do not invent one). A public marketplace is a moderation and security-response commitment; release 1 supports first-party and explicitly pinned modules only.

### A9. UI: SDUI, views, live components

**SDUI (Accepted).** Schema-driven forms, tables, widgets, layouts, navigation, actions, validation and authorization, inspired by legacy panel implementation's fluent API and Webkernel's schemas. The schema is **data first**: a typed builder API that serializes to a declarative form, so the Core panel, API docs and a future visual editor consume the same schema. Output is accessible HTML plus the small client metadata needed for interaction.

**View language.** A familiar template syntax (conditionals, loops, includes, components, slots, escaped output) with its own parser and a bounded expression model, compiled at build time rather than interpreted per request. Inventory existing Webkernel view constructs first; each unsupported one gets a migration path (A6).

**Live components.** Browser events call named server actions; the server validates and authorizes every action and returns only the affected output; the client applies it by DOM morphing, preserving focus and input. Required: loading and error states, validation errors, debounce, lazy islands, CSRF protection, signed component state. **Open decision:** stateless signed snapshots over plain HTTP (Livewire style; simple to scale and cache) versus stateful per-session server state over a persistent connection (LiveView style). Recommendation for v1: stateless.

**Client libraries.** Keep the browser runtime small: a Feluqa-owned runtime for actions and morphing; Alpine.js for local interactions and htmx or Datastar for HTML-over-the-wire as opt-in; Flowbite/Tailwind as a replaceable visual layer; Vue/Svelte only for isolated islands.

**Critique.** Tailwind/Flowbite add a Node build step that contradicts "single binary, simple deploy". Ship a prebuilt CSS layer in the binary and make the Node pipeline optional.

### A10. Ownership and licensing policy

Feluqa and first-party applications are proprietary and distributed only under a separate written license. Third-party dependencies retain their own licenses. The repository license and private registry enforce the intended distribution boundary. Dependency policy:

1. **Own the API surface, not every line.** Each dependency sits behind a Feluqa-named package so users import Feluqa names and upstream names never leak.
2. **Fork and rename only small, stable libraries** you intend to change heavily. For fast-moving engines (backend frameworks, edge servers, database drivers), wrap and pin, with a short patch queue instead of a divergent fork.
3. **Never strip copyright headers or license files.** Generate a `THIRD_PARTY_NOTICES` file. Apache-2.0 requires preserving notices and marking modifications; MIT and BSD require retaining the notice. Renaming namespaces is allowed; claiming original authorship is not. Do not reuse upstream trademarks.
4. **License gate in CI.** Review every transitive license for compatibility with proprietary distribution. Require explicit approval for copyleft, source-available, or custom terms. Do not treat a permissive upstream license as a license for Feluqa itself. Re-check at every upgrade.
5. **Upstream security tracking.** Every vendored or forked component has an owner and a recorded upstream commit; subscribe to advisories and budget time to port fixes.

### Your four questions

#### 1. Nil in Go against no null in Rust

Go has nil pointers, nil maps (writing to one panics), nil interfaces and zero values that hide missing data (an `int` of 0 cannot be told from absent). The classic trap is the typed nil:

```go
func find() error {
    var e *NotFound // nil pointer
    return e        // non-nil error interface: find() != nil is true
}
```

Linters and static analysis (NilAway, errcheck) reduce the risk but the compiler does not enforce it. Rust has no null: absence is `Option<T>`, failure is `Result<T, E>`, the compiler forces both to be handled, and `match` must be exhaustive. The price is that you must write the handling, and some patterns (cyclic structures, shared mutable state) need `Rc`, `Arc`, `Mutex` or index-based designs. For code that must not fail in the field, the real-time profile above all, the compiler-enforced version is worth that price.

#### 2. Boilerplate, side by side

The same handler: parse an id, load an order, render a page, map errors to HTTP statuses.

```go
func getOrder(w http.ResponseWriter, r *http.Request) {
    id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
    if err != nil {
        http.Error(w, "bad id", http.StatusBadRequest)
        return
    }
    order, err := db.GetOrder(r.Context(), id)
    if errors.Is(err, sql.ErrNoRows) {
        http.NotFound(w, r)
        return
    }
    if err != nil {
        http.Error(w, "internal error", http.StatusInternalServerError)
        return
    }
    render(w, orderPage(order))
}
```

```rust
async fn get_order(
    State(db): State<Db>,
    Path(id): Path<i64>,   // a bad id is rejected with 400 automatically
) -> Result<Html<String>, AppError> {
    let order = db.get_order(id).await?.ok_or(AppError::NotFound)?;
    Ok(Html(order_page(&order)))
}
```

Go repeats the error branch at every call. Rust folds it into `?`, but pays elsewhere, once: the `AppError` type (a few lines with the `thiserror` crate, plus one `IntoResponse` implementation that maps variants to status codes), trait bounds, derives, occasional lifetimes, `Send` and `'static` constraints in async code, and slower clean builds. In short, Go is verbose in lines and Rust is dense to read at first. A commonly reported effect with AI agents is that Rust's strict compiler catches more of their mistakes before runtime; measure it in M0 rather than assume it.

#### 3. Dependencies you can see, vendor and rename

Exhibit 3c | Owning dependencies in each ecosystem

| Task | Rust | Go |
| --- | --- | --- |
| Copy all dependency sources into the project | `cargo vendor` creates `vendor/` | `go mod vendor` creates `vendor/` |
| Replace a dependency with your fork | `[patch.crates-io]` or a path dependency | `replace` directive |

| Keep forks beside your code | Cargo workspace with path dependencies and one lockfile | Go workspace (`go.work`) with local modules |
| Expose one namespace | Facade crate `feluqa` re-exporting sub-crates behind feature flags | Facade package; types by alias, functions need wrappers |

Both can show every dependency in your folder. Rust is smoother for "take it and make it mine": renaming a crate touches one line, so a fork merges cleanly with upstream. In Go, renaming rewrites every import, which makes later upstream merges harder.

#### 4. Ecosystem maturity and copying speed

Go's ecosystem is larger for servers and infrastructure (Kubernetes, Docker, Caddy, PocketBase). Rust's is strong in systems tooling, WebAssembly, embedded, web servers, desktop shells and games, and thin in finished backend and admin products. Both are mature enough for the server profile; only Rust is mature across all profiles.

With AI agents, typing a port is cheap; **proving it correct is the cost.** Rank sources to copy by license, size, dependency count and, above all, the quality of their tests. Port protocol (Proposed):

1. Choose a source with a permissive license and an API-level test suite.
2. Record its behavior with black-box tests (HTTP requests and expected responses), which are language-independent.
3. Port in layers (data model, rules, auth, then API), running the black-box suite at each layer.
4. Run differential tests of old against new (FEL-PORT-02).
5. Keep the original license and notices; rename the namespace (A10, Exhibit 3c).

### B3. The finalists

- **Rust leads when scope includes mobile, games, desktop and real-time.** One language, one namespace, no GC, no null, easy forking and renaming. Costs: backend and admin batteries must be ported or built, clean builds are slow, and the learning curve for contributors is steeper.
- **Go leads when scope is web, APIs and desktop.** The fastest route to a working Core panel is to wrap PocketBase, and builds are the fastest. Costs: nil and error boilerplate, GC jitter at p99, and no path to real-time or games.
- **Hybrid is rejected.** Go for the server and Rust elsewhere doubles toolchains and breaks the one-ecosystem goal.
- **Dependence on A5.2.** If app developers write host-language code, build speed weighs heavily; M0 must measure Rust's incremental builds on the real workspace.
- **Mitigating Rust's costs.** Agent-assisted ports verified by black-box tests; vendored and pinned dependencies; the facade crate keeps upstream names out of the public API.

### B6. Recommendation (Accepted after M0)

**Rust is the Feluqa host language.** The pre-registered M0 score is 84.09/100 for Rust and 67.21/100 for Go.
