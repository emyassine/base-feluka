# Decisions still open in the canonical product direction

The owner designated the [Monorepo Architecture](../02.architecture/01.monorepo-architecture.en.md), [Product Document](../01.introduction/02.intent.en.md), and [Compilation requirements](../02.architecture/02.compilation-and-targets.en.md) as controlling. Their decisions supersede older conflicting documentation and records. This page lists choices those canonical documents explicitly leave open; it is not a list of permission requests to re-approve the selected architecture.

## Product Document §10: open questions

1. **Registry trust:** who may publish modules, and where signing trust begins.
2. **Synchronization:** CRDT-first or server-authoritative semantics by data class.
3. **Offline licensing:** how entitlement works on embedded and desktop targets.
4. **Agent approvals:** default approval rules by domain tier and action class.
5. **Watch products:** which features require a phone companion and which can run standalone.

For each, record the selected option, rationale, security consequences and end-to-end acceptance evidence before implementation makes a claim of support.

## Remaining product and migration choices

- **Web/workstation networking:** local or hosted database, device enrollment, routing, offline writes, conflicts, backup and recovery. The bookstore spike in [the workstation plan](../roadmap/05.web-and-workstation-modules.en.md) is the required design evidence.
- **Compiler/MSRV compatibility:** the architecture example proposes workspace toolchain pinning, but final compiler version and target-specific UI feature matrix must be reconciled with actual crate requirements before a release promise.
- **Source layout conventions:** the monorepo diagram fixes top-level workspace/domain groupings. Within a module, agree the scanner's default source discovery and supported overrides before generating code.
- **Historical roadmap mapping:** English/French F8/F9 IDs differ. Retain source-qualified IDs and all acceptance details until a crosswalk can be agreed; do not silently merge checked work or estimates.
- **Documentation languages:** English is normative. Mixed-language pages retain their original text; translation and synchronization remain editorial work.
- **Licensing implementation:** the compile-time embedding note remains exploratory. Decide the entitlement format, trust roots, renewal, revocation and offline policy under the product's module-signing/licensing lifecycle. Compilation must not replace server-side authorization.

## Superseded documentation decisions

The owner-designated architecture resolves these prior conflict categories as target direction: root Cargo workspace and grouped domain crates; System Control Panel and module registry in the platform; UI headless core plus per-target renderers/shells; target core/no_std separation; native shell and bridge architecture; WASM Component Model as the default installable module artifact; agent-native interfaces; and compilation reliability/BI requirements. These targets supersede D-0033 and lower-priority proposals that contradict them. They are not evidence that corresponding crates or runtimes are already delivered.

Do not use the old DOC-01 through DOC-11 migration checklist as pending decisions. Its source records remain in Git and in the migrated chapters for audit, but the owner has now selected the controlling direction above.
