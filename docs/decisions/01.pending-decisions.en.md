## DOC-01 Workspace location and toolchain policy

Sources: [monorepo proposal §2–3](../02.architecture/01.monorepo-architecture.en.md),
[current workspace](../../_crates/Cargo.toml), [Rust standard](../05.reference/03.rust-coding-standard.en.md).

Conflict: the proposal puts Cargo.toml, Cargo.lock and rust-toolchain.toml at the
root and replaces `_crates/` with grouped `crates/`. The current contract keeps
the workspace in `_crates/`, with no root manifest/lock/toolchain pin.

Choose: retain flat `_crates/`; group domains inside `_crates/`; or approve a full
root-workspace migration and explicit toolchain policy. Impact: path dependencies,
workspace members, patches, product `workspace` paths, CLI context discovery,
watcher roots, build/release scripts, registry packaging and every documented
command. Require clean-checkout builds, context tests and generated-product tests
before adoption. No manifest or crate directory was moved by this docs change.

## DOC-03 Crate responsibilities and package names

[auth manifest](../../_crates/feluqa-auth/Cargo.toml),

## DOC-05 Module artifact and trust model

Sources: D-0016/D-0019/D-0022 in [the record](02.platform-vision-record.en.md),
[monorepo proposal §7](../02.architecture/01.monorepo-architecture.en.md).

Conflict: earlier sequencing proposes a core WASM ABI before Component Model;
the monorepo draft declares WASM components the default target and WIT generated
from definitions. Current modules are statically linked. Choose component-first,
staged core-WASM then components, or defer the artifact choice while completing
static lifecycle integration. Native trusted plugins also need an explicit trust
boundary. Require signatures, compatibility, capability denial, bounded execution,
staging/recovery and data-retention tests; M0 call latency proves none of those.
Registry publishers, signing roots and offline licensing remain undecided.

## DOC-08 Compile-time licensing versus runtime entitlement

Sources: [original licensing proposal](04.compile-time-licensing-proposal.en.md),
[licensing guide](../04.for-organizations/02.modules-domains-and-licensing.en.md),
[compilation/cache requirements](../02.architecture/02.compilation-and-targets.en.md).

Conflict: the draft emphasizes per-customer embedded tokens/compile-time stripping;
the platform requires runtime domain authorization and update/revocation behavior.
Its broad OS/JIT/obfuscation and “zero-dependency” crypto claims have not been
validated and are not normative. Choose generic signed entitlements, per-customer
artifacts, or a documented hybrid. Define trust roots, expiry/revocation, offline
behavior, renewal, artifact privacy/cache separation and recovery. No secret may
be emitted into logs/build metadata. Require a threat model and reviewed crypto;
compilation cannot replace per-action authorization. No licensing code is changed.

## DOC-09 Source discovery and authoring conventions

current usage examples.

## How to close a decision

Record the owner's choice, date, rationale, superseded statements and affected
files. Update contracts, translations, crate plan and `AGENTS.md` together; then
implement only the approved scope. Keep rejected proposals and historical test
results identifiable. No DOC-* decision has been closed by this migration.
