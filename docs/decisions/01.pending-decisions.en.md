# Decisions that remain open

The owner has selected two use cases: sensitive organizations that need
disconnected operation, and small businesses that need a local server with
little administration. A supported node hosts Feluqa; nearby devices connect
over the local network without Internet. Shared modules target hosted and local
products. See the [local architecture requirements](../02.architecture/10.local-first-and-air-gapped-runtime.en.md)
and [decisions already made](03.accepted-decisions.en.md).

The remaining questions are about implementation and policy details.

## Trust and licensing

1. **Module trust roots.** The platform must verify packages locally. Which
   trust roots should an organization configure? Can an organization use its
   own public key infrastructure (PKI), a list of approved signing keys, or both?
   Define key rotation, publisher approval and revocation for isolated sites.
2. **Offline license details.** Signed license verification must work locally.
   Decide expiration, renewal, device transfer and whether a license can be
   bound to hardware. Do not require a daily network check.

## Offline writes and synchronization

3. **Conflict policy by data type.** The product must describe how local writes
   continue during network loss and how they merge when devices reconnect. Choose
   where the server remains authoritative and where concurrent changes need
   conflict-free replicated data types (CRDTs), an append-only event log, or
   another explicit rule. The architecture does not select one method for all data.
4. **Peer-to-peer operation.** A local host serving browser and native clients is
   selected. Decide whether separate devices must also synchronize directly when
   no shared host is available. Define recovery and data ownership before promising it.

## Sensitive actions and identity

5. **Approval rules.** Sensitive agent actions require human approval. Specify
   which action types require approval, which roles can approve, how local credentials
   work while disconnected and how emergency overrides are audited.
6. **Device identity and encryption protocols.** The product must support local
   keys, mutual device authentication, auditable identities, protected transport
   and end-to-end encryption for sensitive data. Select identity, enrollment and
   key-lifecycle protocols. A decentralized identifier (DID), mutual Transport
   Layer Security (mTLS) and end-to-end encryption serve different purposes.

## Runtime and product details

7. **Workstation runtime and storage.** Choose the desktop/mobile packaging and
   local database after comparing target support, backup, restore and migration.
   SQLite, RocksDB and sled are candidates, not selected engines.
8. **Watch products.** Decide which functions need a paired phone and which can
   run on a watch directly.
9. **Rust compiler and target matrix.** The architecture requires a pinned Rust
   toolchain. Set its version after checking all supported packages and targets.

## Documentation maintenance

Map English and French roadmap identifiers while retaining each source record and
its evidence. This is editorial work, not a product architecture choice. See the
[migration ledger](../06.governance-and-policy/04.documentation-migration.en.md).

The [compile-time licensing proposal](04.compile-time-licensing-proposal.en.md)
is an exploratory note. It does not replace signed local license checks or
server-side authorization. Never put a private signing key in a product build.
