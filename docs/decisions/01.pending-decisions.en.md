# Decisions that remain open

The [Product Document](../01.introduction/02.intent.en.md) lists five open
product questions. The [workstation plan](../roadmap/05.web-and-workstation-modules.en.md)
adds technical details that need a design and an architecture spike. This page
summarizes the choices that still need answers. Decisions already made are in
[accepted decisions](03.accepted-decisions.en.md).

## Open product choices

1. **Module registry trust.** Who can publish a module? Where do signing keys
   and publisher trust come from?
2. **Live synchronization.** Should the server control final updates for each data
   type, or should devices reconcile concurrent updates using conflict-free
   replicated data types (CRDTs)?
3. **Offline licensing.** How does Feluqa check licenses on desktop and embedded
   products when they cannot reach the licensing service?
4. **Agent approvals.** Which actions need human approval by default for each
   organization type?
5. **Watch products.** Which functions need a paired phone, and which can run
   directly on a watch?

The Product Document records these questions in
[§10](../01.introduction/02.intent.en.md#10-open-questions). Record the selected
answer, its reason and its acceptance evidence here when the owner decides.

## Workstation design questions

The target is one module codebase that can serve a hosted web product and a
standalone workstation product. The user has selected that product direction;
the implementation details remain open.

- Which desktop runtime and local database should the workstation use?
- How should another device connect: through the workstation, a configured host,
  or a peer network?
- How do device enrollment, identity, permissions, transport security and audit
  work across local and remote sessions?
- Which tasks work offline? Can remote devices write? How are concurrent edits
  resolved, and how do backup and recovery work?
- Which UI elements can share their behavior across web, workstation and mobile?

The [bookstore workflow](../roadmap/05.web-and-workstation-modules.en.md) should
answer these questions with implementation evidence before Feluqa claims support.

## Engineering choices to record during implementation

These do not reopen the selected product architecture. The implementation plan
must document:

- The pinned Rust compiler and target matrix that work with the chosen packages.
- The scanner's source discovery defaults and supported overrides within the
  architecture's module layout.
- A source-qualified mapping for French and English roadmap task identifiers.

The original plans and language versions remain in the
[migration ledger](../06.governance-and-policy/04.documentation-migration.en.md).
They preserve their historical details while this mapping is prepared.

## Compile-time licensing note

The [compile-time licensing proposal](04.compile-time-licensing-proposal.en.md)
is an exploratory note. It does not replace the product's signed module lifecycle
or runtime authorization. Resolve license format, trust roots, renewal and
revocation under the open registry and offline licensing questions above. Never
embed a private signing key in a product build.
