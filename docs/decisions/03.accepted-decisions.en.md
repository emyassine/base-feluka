# Decisions already made

These decisions are part of Feluqa's documentation. The owner-designated
[Monorepo Architecture](../02.architecture/01.monorepo-architecture.en.md),
[Product Document](../01.introduction/02.intent.en.md), and
[Compilation requirements](../02.architecture/02.compilation-and-targets.en.md)
are their full specifications. This page gives readers a short index.

A decision marked **Target** sets the direction. It does not claim that the
repository already implements it. See the [implementation baseline](../01.introduction/01.platform-overview.en.md)
and the [crate migration plan](../roadmap/08.crates-change-plan.en.md) for delivery status.

## Product decisions

| Decision | Status | Where it is defined |
|---|---|---|
| Feluqa is one proprietary ecosystem and namespace across web, single-page apps, mobile, desktop, games, APIs and real-time systems. Products share tools and schemas, and use separate target profiles. | Accepted target | [Product intent, §1](../01.introduction/02.intent.en.md#1-product-intent); [profiles, §5](../02.architecture/01.monorepo-architecture.en.md#5-target-profiles-and-constraints) |
| Feluqa hosts installable modules. The platform includes a System Control Panel and module registry. Modules can serve one business area or combine several. The server profile comes first. | Accepted target | [Product model, §§1 and 3](../01.introduction/02.intent.en.md#3-platform-vs-module-model); [workspace map, §2](../02.architecture/01.monorepo-architecture.en.md#2-repository-layout) |
| Feluqa supplies common services and tools. Product teams and their agents build business-specific features in modules. The success measure is the time from a module idea to a working, authenticated, deployed product. | Accepted product direction | [Product intent, §2](../01.introduction/02.intent.en.md#2-strategic-thesis-breadth-is-now-affordable-depth-belongs-to-users) |
| A module declares its identity, version, publisher, license, target profiles, permissions, capabilities, dependencies and public interfaces. | Accepted target | [Module contract, §5](../01.introduction/02.intent.en.md#5-module-contract-summary) |
| Keep release versions consistent across first-party products. Do not use the Feluqa Waterfall codename before version 1.0.0. | Accepted | [Release identity, §8](../01.introduction/02.intent.en.md#8-release-identity) |
| The platform aims to make deployment scriptable and readable by tools. It must not describe the proposed `feluqa deploy` example as a shipped command. | Target | [Deployment, §2.2](../01.introduction/02.intent.en.md#22-the-deployment-problem) |

## Local and disconnected use

| Decision | Status | Where it is defined |
|---|---|---|
| Serve sensitive organizations and small businesses. A supported local node can host Feluqa, and nearby devices can connect without Internet or a cloud service. | Accepted product requirement | [Local products](../02.architecture/10.local-first-and-air-gapped-runtime.en.md#who-feluqa-must-support) |
| Keep module business rules shared between hosted web and local products. Compile shared Rust logic for each supported target and use runtime-specific storage, network and UI adapters. | Accepted target | [Local server and client model](../02.architecture/10.local-first-and-air-gapped-runtime.en.md#local-server-and-client-model) |
| The base product must not require remote content-delivery networks or third-party APIs. Isolated installations need local package verification and an offline update path. | Accepted target | [Disconnected operation](../02.architecture/10.local-first-and-air-gapped-runtime.en.md#disconnected-operation) |
| Sensitive actions require human approval under local authorization policy. Sensitive deployments need local key custody, mutual device authentication, auditable identities, protected transport and end-to-end encryption for data that must remain unreadable to intermediate nodes. | Accepted security requirement; exact protocols and policies remain open | [Local identity and sensitive data](../02.architecture/10.local-first-and-air-gapped-runtime.en.md#local-identity-and-sensitive-data) |
| Verify signed licenses locally so a disconnected installation does not need a daily Internet check. | Accepted requirement; license format, expiry and device binding remain open | [Open licensing questions](01.pending-decisions.en.md#2-offline-license-details) |

## Architecture decisions

| Decision | Status | Where it is defined |
|---|---|---|
| The target Cargo workspace lives at the repository root. Rust packages are grouped by domain under `crates/`; native shells live outside Cargo under `shells/`. Pin the Rust toolchain and define dependency checks. | Accepted target | [Repository layout, §2](../02.architecture/01.monorepo-architecture.en.md#2-repository-layout); [Cargo, §3](../02.architecture/01.monorepo-architecture.en.md#3-cargo-workspace) |
| Select target capabilities through Rust `cfg` conditions and Cargo features, not numbered directory names. Keep Rust language modules distinct from package boundaries. | Accepted | [Architecture constraints](../02.architecture/01.monorepo-architecture.en.md#architectural-constraints) |
| Share UI state and meaning in a headless Rust core. Render it through target-specific web, GPU, native or embedded interfaces. Negotiate shell capabilities. | Accepted target | [UI architecture, §4](../02.architecture/01.monorepo-architecture.en.md#4-ui-architecture-headless-core--native-shells) |
| Keep shared kernel crates usable without the Rust standard library where required. Keep web-server dependencies out of kernel and real-time profiles. | Accepted | [Target profiles, §5](../02.architecture/01.monorepo-architecture.en.md#5-target-profiles-and-constraints) |
| Use the WebAssembly Component Model as the default target artifact for installable modules. Restrict native libraries to trusted first-party use. Keep static linking as the bootstrap path. | Accepted target | [Module system, §7](../02.architecture/01.monorepo-architecture.en.md#7-module-system) |
| Give each module explicit capabilities. The lifecycle includes signing, compatibility and license checks, activation, upgrades and rollback. A rollback of code does not roll back data. | Accepted target | [Module lifecycle, §7.2](../02.architecture/01.monorepo-architecture.en.md#72-lifecycle-and-security); [Product lifecycle, §3](../01.introduction/02.intent.en.md#3-platform-vs-module-model) |
| Version cross-boundary contracts. Add features without removing existing APIs. Require a passing target-specific continuous-integration lane before claiming a target is supported. | Accepted | [Evolvability, §9](../02.architecture/01.monorepo-architecture.en.md#9-evolvability-rules) |

## Agent and supply-chain decisions

| Decision | Status | Where it is defined |
|---|---|---|
| Design the repository and platform for agent use. Keep commands and schemas machine-readable, expose capabilities, test changes, and treat untrusted content as data. | Accepted direction; delivery is staged | [Agent principles, §4](../01.introduction/02.intent.en.md#4-ai-native-by-design); [agent workflow, §10](../02.architecture/01.monorepo-architecture.en.md#10-working-with-ai-agents) |
| Keep the system model-independent. Use distinct agent identities and least-privilege access as the target; approval defaults remain open. | Target, with one open policy choice | [Agent principles, §4.1](../01.introduction/02.intent.en.md#41-principles); [open decisions](01.pending-decisions.en.md#5-approval-rules) |
| Minimize dependencies, pin and review them, and preserve required third-party notices. Never write cryptography, TLS or security-sensitive protocol parsers as an alternative to reviewed libraries. | Accepted policy | [Supply chain, §8](../02.architecture/01.monorepo-architecture.en.md#8-supply-chain-and-dependency-policy); [product policy, §2.3](../01.introduction/02.intent.en.md#23-codebases-and-packages-are-transient-supply-chain-is-a-risk) |

## Compilation and BI decisions

| Decision | Status | Where it is defined |
|---|---|---|
| Measure builds before changing crate boundaries or compiler settings. Preserve deterministic generation and cache invalidation. Cargo owns compiled-artifact fingerprints. | Accepted engineering requirements | [Compilation requirements](../02.architecture/02.compilation-and-targets.en.md) |
| Generate additional Cargo crates before Cargo resolves the build graph. Do not expect a procedural macro or build script to add dependencies after resolution. | Accepted engineering requirement | [Deterministic generation and reuse](../02.architecture/02.compilation-and-targets.en.md#deterministic-generation-and-correct-reuse) |
| Give the development build controller configurable CPU and memory budgets. Preserve the running server on a failed build. Do not promise a zero-downtime handover without readiness and recovery evidence. | Accepted target | [Workstation limits](../02.architecture/02.compilation-and-targets.en.md#keep-the-workstation-usable) |
| Make business-intelligence charts and dashboards part of the shared UI direction. Keep data queries authorized, bounded and separate from rendering. Dashboard data changes must not trigger Rust compilation. | Accepted target | [BI requirements](../02.architecture/02.compilation-and-targets.en.md#built-in-data-visualization-for-business-intelligence) |

## Superseded record

The owner-designated Product Document reinstates the built-in System Panel as a
platform target. It supersedes [D-0033](02.platform-vision-record.en.md#d-0033-no-built-in-system-panel),
which had removed that implementation. The old decision remains in the historical
record; use the Product Document as the current direction.
