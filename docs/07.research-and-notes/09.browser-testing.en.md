Thinking about having a feluqa::testing

Rust est deja compiled donc ca aide mais ca serait bien un `feluqa test:browser <test name or id ...>` or another way so that the browser interractions happen during compilation including authentication through a session etc

En Rust, il n’existe pas d’équivalent unique et "tout-en-un" qui copie exactement la syntaxe de PestPHP (qui repose fortement sur le dynamisme de PHP et ses fermetures globales). Cependant, vous pouvez obtenir une expérience de test d'interaction de navigateur très proche en combinant un moteur d'automatisation de navigateur moderne avec une bibliothèque d'assertions fluides.
Le paysage Rust se divise en deux catégories pour répondre à ce besoin :

1. Les moteurs de navigation (L'équivalent de Dusk / WebDriver)

Pour piloter un vrai navigateur (Chrome/Firefox) et interagir avec la page (clics, saisies, navigation), les meilleures options actuelles sont :
• thirtyfour : C’est la bibliothèque la plus mature et la plus populaire pour le test d'interface utilisateur en Rust. Elle est basée sur le protocole W3C WebDriver (compatible avec Selenium, Chrome, Firefox) et supporte nativement async/await via Tokio. [1] (https://docs.rs/thirtyfour)
• chromiumoxide : Idéal si vous préférez une connexion directe via le protocole Chrome DevTools (CDP) plutôt que de passer par un binaire WebDriver lourd. C'est une excellente alternative légère de type Puppeteer en pur Rust. [1] (https://dev.to/vhub_systems_ed5641f65d59/headless-browsers-in-rust-chromiumoxide-vs-headlesschrome-vs-the-python-alternative-25e5)
• browser-test : Un outil plus récent conçu spécifiquement comme un "test runner" pour l'intégration de tests de navigation asynchrones sous Rust en se basant sur Chrome for Testing et thirtyfour. [1] (https://crates.io/crates/browser-test/security), [2] (https://github.com/lpotthast/browser-test)

2. Syntaxe fluide et expressive (L'équivalent de la syntaxe "Pest")

PestPHP brille par sa syntaxe chaînée expect($value)->toBe(). Pour reproduire ce confort de lecture et d'écriture en Rust, vous pouvez greffer l'une de ces bibliothèques sur votre suite de tests :
• fluent-test : Fortement inspirée des frameworks JavaScript (comme Jest), elle offre une syntaxe de chaînage très propre via la macro expect! (ex: expect!(titre).to_contain("Mon App");). [1] (https://docs.rs/fluent-test), [2] (https://crates.io/crates/fluent-test)
• fluent_assertions : Permet également d'écrire des assertions sous forme de phrases lisibles en chaînant des méthodes directement après un appel .should() (ex: "Mon bouton".should().be_visible()). [1] (https://docs.rs/fluent-assertions)
• rstest : Si vous aimiez la gestion des fixtures et le paramétrage de Pest, rstest est incontournable en Rust pour injecter des états complexes ou des instances de navigateurs réutilisables dans vos fonctions de test. [1] (https://crates.io/crates/rstest-bdd)

Exemple concret de ce à quoi cela ressemble

En combinant thirtyfour (pour le navigateur) et fluent-test (pour le style Pest), votre code de test ressemblera à ceci :
rust
use thirtyfour::prelude::*;
use fluent_test::prelude::*;

#[tokio::test]
async fn test_interaction_connexion() -> WebDriverResult<()> {
    // Configuration du navigateur
    let caps = DesiredCapabilities::chrome();
    let driver = WebDriver::new("http://localhost:9515", caps).await?;

    // Équivalent de $browser->visit(...)
    driver.goto("https://mon-application.local").await?;

    // Interaction : Remplir le formulaire
    let email_input = driver.find(By::Id("email")).await?;
    email_input.send_keys("user@example.com").await?;

    let submit_btn = driver.find(By::Tag("button")).await?;
    submit_btn.click().await?;

    // Assertion style "Pest / Fluent"
    let url_actuelle = driver.current_url().await?.to_string();
    expect!(url_actuelle).to_contain("/dashboard");

    driver.quit().await?;
    Ok(())
}
Utilisez le code avec précaution.
Pour vous orienter au mieux, utilisez-vous déjà un framework web spécifique côté Rust (Axum, Actix-web, Rocket) pour votre application, ou s'agit-il de tester un site externe déjà déployé ?
