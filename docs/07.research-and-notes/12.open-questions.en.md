# Open architecture questions and proposals

**Status:** proposals for owner review. None of the implementation choices below
has been approved. English is the working language for this register. The
selected product requirements are documented in the [product intent](../01.introduction/02.intent.en.md),
[local architecture](../02.architecture/10.local-first-and-air-gapped-runtime.en.md)
and [organization security guide](../04.for-organizations/03.data-and-security.en.md).

This register groups open choices by stable identifier. When the owner selects
an option, move the accepted rule into its domain document, record its rationale
and consequences there, and remove the item from this register. Keep historical
source records in the research archive; `docs/decisions/` is not a permanent
section of the documentation tree.

The recommendations below are unverified proposals, not security guidance or
compatibility claims. Compare maintained implementations, target support,
licenses, threat models and recovery behavior before selecting them.

## Trust, licensing and approval

### DEC-001-MODULE-SIGNING — Module signing and offline revocation

**Open choice:** How does each organization establish trusted module publishers,
rotate keys and revoke compromised keys when installations cannot reach a
central service?

**Proposal to evaluate:** Keep a root key offline, delegate to organization
keys, and use release-signing keys for packages. Evaluate Ed25519 signatures,
Minisign-compatible tooling and locally distributed signed revocation lists.
A local revocation list can be stale while disconnected; define its validity,
expiry, emergency update and audit rules before relying on it.

**Domain document:** [Modules, domains and licensing](../04.for-organizations/02.modules-domains-and-licensing.en.md).

### DEC-002-OFFLINE-LICENSING — Offline license format and device binding

**Open choice:** Define license validity, renewal, transfer, feature claims and
hardware binding without requiring daily Internet access.

**Proposal to evaluate:** Use an asymmetrically signed, structured token. Compare
JWT and PASETO implementations. Make hardware binding optional by deployment
profile; compare migration and recovery costs with the security benefit. CPU,
network-card and other changeable hardware fingerprints can lock out legitimate
customers and are not a substitute for a hardware-backed identity.

**Domain document:** [Modules, domains and licensing](../04.for-organizations/02.modules-domains-and-licensing.en.md).

### DEC-005-AGENT-APPROVAL — Human approval for sensitive agent actions

**Open choice:** Define the action classes that require approval, eligible local
roles, disconnected credentials, emergency override and audit requirements.

**Proposal to evaluate:** Combine local role-based access control (RBAC) with
attribute checks (ABAC) or scoped capability tokens. Evaluate Macaroons only if
their caveat and revocation model fits disconnected operation. Consider a local
PIN or hardware authenticator for approval. Define separation of duties and
replay protection; the examples in the proposal are not selected policy.

**Domain documents:** [Data and security](../04.for-organizations/03.data-and-security.en.md)
and [authorization guide](../03.for-developers/07.authorization.en.md).

### DEC-006-DEVICE-IDENTITY-AND-CRYPTO — Device identity, transport and encryption

**Open choice:** Select enrollment, identity, key storage, rotation, revocation,
transport protection, end-to-end encryption and backup/recovery protocols.

**Proposal to evaluate:** Compare TLS 1.3 with organization-managed mutual TLS
(mTLS) certificates against the Noise Protocol Framework for supported links.
Select authenticated encryption for stored data based on reviewed libraries and
target support. AES-256-GCM and ChaCha20-Poly1305 are candidates to compare,
not selected algorithms. Compare hardware-backed keys with a password-derived
key where the threat model calls for it. Argon2id is a password key-derivation
candidate; it does not replace a key-management design. End-to-end encryption
also needs recipient discovery, key change and recovery rules.

**Domain document:** [Data and security](../04.for-organizations/03.data-and-security.en.md).

## Data and runtime

### DEC-003-OFFLINE-SYNC — Synchronization and conflict policy by data type

**Open choice:** Define which records can be edited offline, which node is
authoritative, and how concurrent updates, deletion and recovery work for each
data type.

**Proposal to evaluate:** Use append-only event records for audit and selected
telemetry, with causal ordering where required. Evaluate CRDTs for data that
needs concurrent collaborative editing. A local host can be the normal
convergence point without being the only possible merger. Define idempotence,
retention, privacy and conflict-resolution behavior before selecting either
model. Evaluate Lamport or vector clocks where causal ordering is needed;
wall-clock timestamps alone do not establish causality.

**Domain document:** [Local and disconnected architecture](../02.architecture/10.local-first-and-air-gapped-runtime.en.md).

### DEC-004-PEER-TO-PEER — Direct device synchronization

**Selected baseline:** A local Feluqa host serves nearby clients.

**Open choice:** Is direct device-to-device synchronization required when the
host is unavailable, or is host failover sufficient?

**Proposal to evaluate:** Treat peer discovery and transfer as a later extension.
Compare local discovery such as mDNS with an authenticated replication layer.
The proposal mentions Babel and libp2p; assess whether either matches the actual
network and threat model. Specify ownership, split-brain handling, reconciliation
and device-loss recovery before adding this mode.

**Domain document:** [Local and disconnected architecture](../02.architecture/10.local-first-and-air-gapped-runtime.en.md).

### DEC-007-WORKSTATION-RUNTIME-AND-STORAGE — Local runtime, database and packaging

**Open choice:** Select workstation/mobile packaging, local persistence and
backup/restore behavior while keeping module business rules shared.

**Proposal to evaluate:** Compare a local HTTP server with a progressive web app
(PWA) against a native shell such as Tauri. Compare SQLite for relational,
transactional workloads with embedded alternatives such as redb or fjall where
Rust-only implementation is a requirement. Evaluate rusqlite as one SQLite
binding. Existing architecture notes also list RocksDB and sled. Evaluate
migration, concurrency, portability, encryption, operations and dependency
costs; none of these candidates is selected here.

**Domain document:** [Local and disconnected architecture](../02.architecture/10.local-first-and-air-gapped-runtime.en.md).

## Product and toolchain

### DEC-008-WEARABLES — Standalone and companion watch features

**Open choice:** Decide which workflows require a paired phone and which must
work on a watch without a network connection.

**Proposal to evaluate:** Consider bounded local capture, notifications and
buffering for standalone use. Consider broader synchronization and heavy work
as companion functions. Validate safety, battery, storage and recovery needs
before setting product scope.

**Domain document:** [Product intent](../01.introduction/02.intent.en.md).

### DEC-009-RUST-TOOLCHAIN-AND-TARGETS — Compiler and target matrix

**Open choice:** Pin a Rust toolchain and define release/CI target lanes after
checking the actual dependencies, shells and product profiles.

**Proposal to evaluate:** Compare `x86_64-unknown-linux-gnu` and
`aarch64-unknown-linux-gnu` for server/workstation; `x86_64-pc-windows-msvc`,
`x86_64-apple-darwin` and `aarch64-apple-darwin` for desktop;
`wasm32-unknown-unknown` and `wasm32-wasip1` for WebAssembly; and
`aarch64-linux-android` and `aarch64-apple-ios` for mobile. Confirm each target
against the actual runtime, dependencies and CI environment before selecting
it. The supplied `1.82+` example is not a selected MSRV or a validated current
recommendation. Define which targets must compile, run tests or receive release
artifacts; do not call a target supported based on compilation alone.

**Domain document:** [Rust coding standard](../05.reference/03.rust-coding-standard.en.md)
and [target profiles](../02.architecture/01.monorepo-architecture.en.md).
